## 第 0 章:這份要回答什麼

### 這五個問題

這份文件的章節順序,是照**讀者實際問過的問題**排的:

1. **A2A 到底處理哪一段?**
2. **它是應用層嗎?**
3. **Agent Card 在程式碼裡長什麼樣?**
4. **它有哪些動詞?有沒有區分「聊天」跟「任務」?**
5. **contextId 是什麼?**

如果你現在對這五個問題都沒感覺,那很正常 —— 讀完第 1 章你就會開始想問第 2 個。

### 先給你一張定位圖

第 2 章會完整解釋,現在先看一眼就好,它能治「這東西到底站在哪」的焦慮:

```
    ┌─────────────────────────────────────────┐
    │  A2A          agent 之間怎麼交辦事情      │  ← 這份文件在講這一層
    ├─────────────────────────────────────────┤
    │  JSON-RPC     怎麼「呼叫對方的一個功能」   │
    ├─────────────────────────────────────────┤
    │  HTTP         請求與回應的信封格式        │
    ├─────────────────────────────────────────┤
    │  TCP          確保字元送得到、順序不亂     │
    └─────────────────────────────────────────┘
```

**每一層都假設下面那層已經解決了。** A2A 從來不管「網路斷了怎麼辦」——
那是 TCP 的事;它只管「一個 agent 要請另一個 agent 做事,那句話該長什麼樣」。

### 這份文件裡的兩種聲音

★ **這是全篇最重要的閱讀規則。**

我們自己就跑著一套 A2A 實作,所以文件裡會不斷出現真實的例子。但**規格說的**跟
**我們做的**是兩件事,混在一起讀會出問題 —— 你去看別人的 A2A 實作時會困惑
「為什麼他們沒有這個東西」。

所以凡是「我們的做法」,一律用這個框標起來:

> ▌**本專案**
> 這種框裡的東西是**我們的選擇**,不是規格的規定。規格允許很多種做法,我們挑了一種。

沒有框的部分,就是協定本身。

### 讀完你會知道什麼

- A2A 管什麼、**刻意不管什麼**(後者更重要)
- 一個 agent 怎麼被別人「找到」與「認識」
- 「訊息」跟「任務」差在哪 —— 以及為什麼 A2A 的字典裡**沒有「純聊天」這個詞**
- 多 agent 系統的三種基本形狀,以及每種形狀裡誰是 client、誰是 server
- 最後你會拿 `curl` 對著自己電腦上那台 hub,真的走一次完整的交辦流程

### 這份沒有要做的事

它不是規格的翻譯。**凡是我們沒有實作過的東西,我不會假裝教你怎麼用** ——
只會提名字、一句話說明、放進附錄。理由很簡單:我寫不出可驗證的例子,
而一個沒跑過的例子就是下一個會過期的謊。

## 第 1 章:兩個 AI 要合作,少了什麼?

### 生活類比:找隔壁公司幫忙

你的公司要出貨,但貼標這道工序要外包給隔壁那家。於是你打電話過去:

> 「喂,我要五百張標籤,明天下午要,規格是這樣……」

這通電話能成立,是因為你們**事先講好了很多事**:用電話而不是傳心術、
講中文而不是德文、「明天下午」指的是哪一天、以及**對方會給你一個單號讓你追進度**。

現在換成十家公司互相外包。如果每一對都自己講好一套規矩 ——
甲乙用電話、甲丙用傳真、乙丙用 email 而且格式還不一樣 ——

**十家兩兩配對是 45 種組合。** 你要維護 45 套規矩。

再加入第十一家,你得再談 10 套。這就是所謂的 **N×N 問題**:
成本不是跟著參與者的數量長,是跟著**配對的數量**長。

### 解法:大家講同一種話

如果十一家公司都同意「我們一律用同一份訂單格式」,那就只有**一套**規矩。
新的公司加入時,它學那一套就能跟所有人做生意。

> **協定(protocol)** 這個詞不用怕,它就是「**事先講好的溝通格式**」。
> 郵局規定信封上收件人寫哪、地址寫哪,那就是一種協定。

### 這跟 AI 有什麼關係

**agent** 這個詞在這份文件裡的意思是:**會自己動手做事的 AI**。
不是「你問它答」那種,是你交辦一件事、它自己去做、做完回報你的那種。

當你只有一個 agent 時,沒有協定問題 —— 它跟你講話就好。
但當你有好幾個 agent、而且它們要**互相交辦**時,N×N 問題就出現了:

- Google 做的 agent、OpenAI 做的 agent、你自己寫的 agent
- 每一對之間都要一套翻譯

**A2A(Agent-to-Agent Protocol)就是那份公定的訂單格式。**
它由 Linux 基金會維護 —— 就像 HTTP 是所有網站的共通語言、USB 是所有隨身碟的共通接口。

### ★ 一個新手一定會卡的地方:誰是 client、誰是 server

這兩個詞在 A2A 裡**會互換**,而且沒有人會提醒你。

- **client** = 提出要求的那一方
- **server** = 接受要求、負責做事的那一方

**同一個 agent,在不同的時刻是不同的角色:**

```
你 ──派任務──▶ alice        這時 alice 是 server
                  │
                  └──派任務──▶ bob     這時 alice 是 client、bob 是 server
```

生活裡完全一樣:餐廳的服務生對客人來說是 server(接受點餐),
對廚房來說是 client(他去下單)。**同一個人,兩個角色,取決於你站在哪一邊看。**

**為什麼這件事值得單獨講**:很多教學會寫「A2A 是 client-server 協定」,
讀者就以為有一邊天生是伺服器。實際上 **A2A 的重點正是「每個 agent 兩種角色都能當」**——
不然它就沒辦法組成一個網,只能組成一棵樹。

> ▌**本專案**
> 我們的每個 agent 都同時是兩種角色:alice 可以被你派任務(server),
> 也可以自己去派任務給 bob(client)。你在第 8 章會看到這決定了整個系統的形狀。

### 一句話收束

> **協定解決的不是「怎麼講話」,是「不用為每一對關係各發明一次怎麼講話」。**

## 第 2 章:它疊在誰上面?

讀者問過的第二個問題是「**A2A 是應用層嗎?**」——
這一章要說明,那個問題的答案比「是」或「不是」有意思。

### 生活類比:寄一份合約

你要寄一份合約給對方公司。這件事**同時發生了四件事**,而且每一件都有自己的規矩:

| 層次 | 誰在管 | 規矩長什麼樣 |
|---|---|---|
| 這份合約在講什麼生意 | 你跟對方 | 「五百張標籤、明天下午、單價多少」 |
| 公文的格式 | 公司的文書規範 | 主旨寫哪、簽名蓋哪 |
| 信封怎麼寫 | 郵局 | 收件人寫右下、郵票貼右上 |
| 信怎麼送到 | 郵務系統 | 分揀、運輸、投遞 |

**上面那層完全不管下面那層怎麼做到的。** 你寫合約時不會去想郵差走哪條路。

### 網路上的同一疊

```
    ┌─────────────────────────────────────────────────────┐
    │  A2A          「我要交辦一件事,它現在做到哪了」        │
    ├─────────────────────────────────────────────────────┤
    │  JSON-RPC     「我要呼叫你的哪個功能,參數是什麼」       │
    ├─────────────────────────────────────────────────────┤
    │  HTTP         「這是一個請求,那是一個回應」            │
    ├─────────────────────────────────────────────────────┤
    │  TCP          「這些字元會到、而且順序不亂」            │
    └─────────────────────────────────────────────────────┘
```

由下往上看,每一層都在**替上面那層省事**:

- **TCP** 保證你送出去的字元會完整抵達、順序正確。沒有它,你得自己處理封包遺失。
- **HTTP** 講好「一問一答」的形狀 —— 有請求就有回應,還有狀態碼(200 成功、404 找不到)。
- **JSON-RPC** 再上一層:它把「呼叫對方的一個函式」這件事標準化。
  你送過去的是 `{"method": "GetTask", "params": {...}}`,對方回你結果或錯誤。
- **A2A** 站在最上面,它規定的是**那些函式叫什麼、以及它們在講什麼事**。

### 所以「是應用層嗎」的答案是

**是,而且它是應用層裡最上面的那一層。**

更精確的說法是:**A2A 是一套「概念」,不是一套「線路格式」。**
同一套概念可以搭在不同的載具上 —— 就像同一份合約可以用郵寄、可以用 email、可以用傳真。

> **給有嵌入式背景的讀者**:這跟 **Modbus** 是同一個結構。
>
> Modbus 定義的是「功能碼」的語意 —— 03 是讀保持暫存器、06 是寫單一暫存器。
> 那套語意**跟它跑在什麼線上無關**:`Modbus RTU` 跑在 RS-485 上、
> `Modbus TCP` 跑在乙太網上,而**功能碼的意思一個字都沒變**。
>
> A2A 也一樣:`SendMessage`、`GetTask` 這些「功能碼」的語意是固定的,
> 而它可以用 JSON-RPC 送、也可以用別的方式送。**規格把這叫做 binding(綁定)。**
>
> (類比的邊界:Modbus 是主從式,從站不會主動找主站;A2A 的兩端可以角色互換 —— 見第 1 章。)

> ▌**本專案**
> 我們用的是 **JSON-RPC binding**,端點是 `POST /agents/{名字}/a2a`。
> 這是我們挑的一種,不是唯一一種。你在第 3 章會看到 Agent Card 裡有一個
> `protocolBinding: "JSONRPC"` 欄位,那就是在告訴別人「我這台講這種」。

### ★ 一個很自然、但差一步的直覺:「所以 A2A 像交握?」

讀到這裡,有網路或韌體背景的人常常會這樣理解:

> 「HTTP 負責夾帶內容,JSON-RPC 負責內容的格式,
>   那 A2A 就是**雙方交握的流程**,對嗎?」

**這個直覺對了一半,而差的那一半很關鍵。**

**交握(handshake)是一次性的開場程序** —— 像 TCP 的三次握手、
像 TLS 交換金鑰:雙方先確認彼此能講話、講定參數,**然後交握就結束了**,
接下來傳什麼它不管。

**A2A 不是開場,是全程。** 它管的是從「我怎麼知道你存在」一路到「這件事結案了」的整段:

```
   交握            ├──┤                              一次性,講定就退場
   A2A     ├───────────────────────────────────┤    從見面到結案,全程都在
           發現對方   下單   對方在做   要補資料   結案
```

**更貼切的說法:A2A 是一份合作契約,不是一次自我介紹。**
契約會規定「工單長什麼樣」「做到一半要怎麼回報」「做不完算誰的」——
這些全都發生在交握**之後**,而交握對它們一句話都沒說。

> 為什麼這個誤讀值得單獨拿出來講:因為它會讓你**低估這個協定的範圍**。
> 以為是交握的人,會去找「連線建立」那一段;而 A2A 的重點全在連線建立**之後**。

### 那 MCP 站在哪裡?

你可能聽過 **MCP(Model Context Protocol)**。它跟 A2A **同一層,但管不同的事**:

| | 管什麼 | 一句話 |
|---|---|---|
| **MCP** | agent 怎麼**用工具**(查資料庫、讀檔案、呼叫 API) | 像**插座** —— 把能力插進 agent 裡 |
| **A2A** | agent 怎麼**找另一個 agent** 交辦事情 | 像**電話** —— 打給另一個會自己做事的對象 |

差別在於**對方有沒有自主性**:工具不會拒絕你、不會問你問題、不會做到一半說「我需要更多資訊」。
另一個 agent 會。

> 想知道業界怎麼把這兩個湊在一起用(以及哪些做法已經死了),
> 看 `doc/ECOSYSTEM.md` —— 那份有實查的數據與各自的下場。這裡不重複。

### 一句話收束

> **問「A2A 是不是應用層」,等於問「合約是不是紙」。**
> 它是應用層最上面那一層,而它的價值來自它假設了下面三層都已經被解決 ——
> **一個協定能規定得多精確,取決於它敢假設多少事情不用自己管。**

## 第 3 章:名片 —— 你怎麼認識一個從沒打過交道的 agent

讀者問過的第三個問題是「**Agent Card 在程式碼裡怎麼呈現?可以直白一點嗎?**」
這一章會直接把我們 hub 上一張**真的**名片攤開來看。

### 生活類比:第一次找一家沒合作過的工廠

你想找一家工廠代工。問題來了:

> 你想問他「你們做什麼、怎麼下單」——
> **但你連「該怎麼問他」都還不知道。**

這是個先有雞還是先有蛋的問題。現實世界的解法是**把答案放在一個大家都知道的地方**:
招牌掛在門口、型錄放在櫃台、電話印在招牌上。你不用先認識他,走到門口就看得到。

### A2A 的做法:固定網址上的一份 JSON

每個 agent 都在一個**固定的路徑**上放一份自我介紹,叫 **Agent Card(名片)**:

```
https://某某網域/.well-known/agent-card.json
```

`.well-known/` 這個路徑不是 A2A 發明的,它是網路上的老慣例(RFC 8615)——
「**這個資料夾底下放的是機器要讀的自我介紹**」。很多東西都用它:網站的憑證驗證、
密碼管理器要找的「改密碼頁面在哪」,都放這裡。

> **關鍵在於「固定」。** 如果每家 agent 把名片放在自己喜歡的路徑,
> 你就得先問他「名片在哪」—— 而那又回到雞生蛋。
> **約定一個位置,才能讓「第一次接觸」不需要任何前置知識。**

### 一張真的名片

下面這張是從我們自己那台 hub 抓下來的,不是我編的:

```json
{
  "name": "alice",
  "description": "透過敲鈴器連線的 agent(名字:alice)",
  "supportedInterfaces": [
    {
      "url": "http://127.0.0.1:8787/agents/alice/a2a",
      "protocolBinding": "JSONRPC",
      "protocolVersion": "1.0"
    }
  ],
  "version": "1.0.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false,
    "extendedAgentCard": false
  },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "skills": []
}
```

### 逐欄看它在說什麼

| 欄位 | 白話 |
|---|---|
| `name` / `description` | **我是誰。** 給人看的 |
| `supportedInterfaces` | **怎麼跟我說話。** 打哪個網址、用哪種 binding、協定第幾版 |
| `version` | **我這個 agent 的版本**(注意:不是協定的版本,協定版本在上一欄裡) |
| `capabilities` | **我支援哪些選配功能** |
| `defaultInputModes` / `OutputModes` | **我吃什麼、吐什麼**(用 MIME 類型講,這裡是純文字) |
| `skills` | **我會做哪些事** |

`supportedInterfaces` 是**陣列**,因為同一個 agent 可以同時支援多種講法 ——
就像第 2 章那個 Modbus 的例子:同一套語意,RTU 跟 TCP 兩種載具都給你。

### ★ `capabilities` 最值得看:它是「我不支援什麼」的誠實聲明

```json
"capabilities": {
  "streaming": true,           ← 我支援串流(邊做邊回報)
  "pushNotifications": false,  ← 我【不】支援回呼,別對我用那招
  "extendedAgentCard": false
}
```

這個設計很實際:**與其讓對方試了才知道會失敗,不如一開始就講清楚。**

沒有這個欄位的話,client 只能「先試試看,收到錯誤再換一招」——
而那代表每一次接觸都要浪費一輪往返,還要處理一堆錯誤分支。

> **這是協定設計的一個通則:能在「自我介紹」階段講清楚的,就不要留到「出錯」階段才發現。**

### ★★ 一個很好的誠實教材:`skills` 是空的

你注意到 `"skills": []` 了嗎?**規格有這個欄位,而我們沒有填。**

`skills` 的用途是讓別人挑:「我要找一個會翻譯的 agent」——
去讀名片,看誰的 skills 裡有翻譯。

> ▌**本專案**
> 我們沒填,因為我們的 agent 是**通用的聊天室成員** ——
> 它們不是「翻譯專家」或「訂票專家」,而是「跟你一起工作的同事」,
> 事先列不出一份技能清單。而且在我們的系統裡,**沒有任何程式會去讀那個欄位**。
>
> 填一份沒人讀的清單,只會變成下一個要維護、而且遲早跟事實不符的東西。
> 所以我們**刻意留空**,而不是隨便填幾個好看的。

### ★★★ 名片是身分證,不是房卡

這是我們真的踩過的坑,值得寫在這裡。

我們的聊天室有「房間」的概念。有一版的實作把名片綁在房間上 ——
結果是「alice 在 A 房的名片」跟「alice 在 B 房的名片」變成兩個不同的東西,
而 B 房沒有她的話,去要名片就得到 404。

**那是錯的。** 名片回答的是「**這個 agent 是誰、怎麼找它**」,那是它的**身分**,
跟它現在人在哪個房間無關。

> **判準**:名片是**身分證**,不是**房卡**。
> 身分證不會因為你換了一棟大樓就失效。

### 一句話收束

> **名片解決的是「第一次接觸」——而第一次接觸的難處不是不會講話,是不知道該對誰講、用什麼講。**
> 一個協定要能長大,它必須讓陌生人不需要任何前置知識就能開始。

## 第 4 章:一句話的形狀 —— 以及為什麼 A2A 沒有「純聊天」

### 生活類比:便條紙與公文

同一句話「明天下午要五百張標籤」,寫在兩種紙上,意義完全不同:

| | 便條紙 | 公文 |
|---|---|---|
| 有沒有編號 | 沒有 | 有文號 |
| 屬於哪個案子 | 不屬於任何案子 | 掛在某個案號底下 |
| 丟了會怎樣 | 就沒了 | 收發紀錄查得到 |
| 誰要負責 | 沒人 | 承辦人 |

**A2A 的訊息全部是公文,沒有便條紙。** 這一章要說明這句話的意思。

### 一則 Message 長什麼樣

```json
{
  "messageId": "隨機產生的唯一編號",
  "role": "ROLE_USER",
  "parts": [{"text": "幫我看一下這段程式"}],
  "contextId": "這句話屬於哪一段對話",
  "taskId": "這句話屬於哪一件任務"
}
```

四個欄位,各自回答一個問題:

**`role` —— 誰在說**

只有兩個值:`ROLE_USER`(提出要求的那方)與 `ROLE_AGENT`(做事的那方)。

★ 注意它是**角色**不是**身分**。第 1 章講過 client / server 會互換 ——
所以同一個 agent,這則訊息裡是 `ROLE_AGENT`,下一則去交辦別人時就是 `ROLE_USER`。

**`parts` —— 內容,而且是一個陣列**

為什麼不直接放一個字串?因為一則訊息可以**同時**有好幾種東西:
一段文字 + 一張截圖 + 一個結構化的資料表。

```json
"parts": [
  {"text": "這是報表"},
  {"file": {...}},
  {"data": {...}}
]
```

**一則訊息 = 好幾個 part 的組合**,就像一封 email 可以有正文加附件。

這個設計的價值不在「現在能放三種東西」,在於**「內容的形式」可以長出新種類,
而「訊息」這個概念一個字都不用改** —— 哪天多一種 part,舊的 client 照樣看得懂
它認得的那幾個,只是忽略不認得的。

> 如果 `parts` 當初設計成一個字串,今天要加附件就得改「訊息」本身的定義 ——
> 而改定義意味著**所有既有的實作都要跟著改**。
> **留擴充口的成本是現在多一層陣列;不留的成本是未來所有人一起改。**

> ▌**本專案**
> 我們**只支援文字**(`TextPart`)。不是規格只有文字,是我們只做了文字 ——
> 因為我們的聊天室就是文字介面,做圖片與檔案沒有消費端。

**`messageId` —— 由發送方生成**

這一點常被問:為什麼不是伺服器發號碼?

因為**發送方需要在送出去之前就知道這則的編號**。有了它,
重送同一則時對方認得出「這是同一則,不要做兩次」,而回覆時也能明確指出在回哪一則。

**`contextId` / `taskId` —— 它掛在哪**

這兩個是下一章的主角。現在你只要記住:**每一則訊息都掛在某個東西底下。**

### ★★ 核心的一句話:A2A 的字典裡沒有「純聊天」

翻遍 A2A 的規格,你找不到一個叫「chat」或「聊天」的東西。

**每一則訊息都必須說出它屬於哪一段脈絡** —— 而通常還會說出它屬於哪一件任務。
沒有「我就是隨口講一句,不屬於任何事」這種東西。

**為什麼?因為這個協定的目的是「交辦與追蹤」,不是社交。**

回想第 1 章那個外包的例子:你打電話給工廠,說的每一句話都掛在某張訂單底下。
「你們最近好嗎」這種話不會進訂單系統 —— **不是因為它不重要,是因為訂單系統管不了它。**

> **這件事的實務後果**:如果你想做一個「AI 們可以閒聊」的系統,
> A2A 不會幫你 —— 你得自己做那一層。它只保證「交辦這件事」不會亂。

> ▌**本專案**
> 我們的聊天室**大部分都是純聊天**。直接數 `hub_data/chat.jsonl`(2026-07-28):
> **main 房 835 則訊息,其中只有 4 則是真正的 A2A 任務** —— 0.48%。
>
> 那 831 則聊天**完全不進協定的狀態機** —— 對 A2A 那一層來說它們不存在。
> 它們只活在我們自己做的「可視化層」裡(就是你在瀏覽器看到的那個聊天室)。
>
> 換句話說:**我們在 A2A 旁邊自己蓋了一個聊天室,而不是用 A2A 蓋聊天室。**
> 這個區分很重要 —— 下一章你會看到那 4 則跟那 831 則的待遇差多少。
>
> (數字會變,方法不會:`hub_data/chat.jsonl` 裡帶 `task_id` 的就是任務。
>  要數房間總共幾則,用 `GET /api/rooms/main/state` —— 它直接回 `count`。)

### 一句話收束

> **一則訊息的形狀,洩漏了那個協定在乎什麼。**
> A2A 的訊息一定要說「我屬於哪件事」——
> 因為它從頭到尾在解的問題是「**這件事現在怎麼樣了**」,而不是「我們聊得開不開心」。

## 第 5 章:工單 —— 動詞、狀態,以及「這件事屬於哪個案子」

這一章回答讀者問過的第四、五個問題:
**「它有哪些動詞?有沒有區分一般訊息跟交付任務?contextId 又是啥?」**

### 生活類比:點餐 vs 修車

**在餐廳點餐**:你說「一份牛肉麵」,廚房做,做好上桌。中間你不會打電話問進度,
因為它十分鐘就好,而且不會做到一半打給你。

**送車去修**:完全不一樣。修車廠會給你一張**工單**,上面有單號。你可以打電話問
「我的車修到哪了」,對方可能回你「還在等零件」;修到一半他可能打給你說
「煞車皮也該換了,要換嗎?」——**而這通電話你不接,他就沒辦法繼續。**

**A2A 的 Task 是工單,不是點餐。** 它假設的是「這件事要做一段時間,而且中途可能有狀況」。

### 動詞有哪些?七個

| 動詞 | 白話 |
|---|---|
| `SendMessage` | **交辦一件事**(或就只是說句話 —— 見下一節) |
| `SendStreamingMessage` | 同上,但要對方**邊做邊回報** |
| `GetTask` | 那件事現在怎麼樣了? |
| `ListTasks` | 我手上有哪些事在跑? |
| `SubscribeToTask` | 有變化的時候**通知我**,我不想一直問 |
| `CancelTask` | 算了,不用做了 |
| `GetExtendedAgentCard` | 給我看你的**進階版名片**(要先通過認證的那種) |

★ **值得停下來看一眼的觀察**:七個動詞裡,**有三個在問「現在怎麼樣了」**
(`GetTask` / `ListTasks` / `SubscribeToTask`)。

這洩漏了這個協定的重心:**它一半的心力花在「追蹤」,不是「交辦」。**
交辦一句話就講完了;難的是交辦之後那段你看不見的時間。

### ★★ 「有沒有區分一般訊息跟交付任務?」—— 答案很妙

**你只有一個動詞可以送話:`SendMessage`。** 沒有「SendChat」跟「SendTask」兩個。

那怎麼區分?**規格把這個決定權交給了接收方,不是你。**

規格的原話是這個意思:收到訊息的 agent **可以**開一張新工單,**也可以**直接回你一則訊息。
**同一個動詞,兩種可能的結果,由做事的那一方決定。**

**為什麼這樣設計?** 因為「這件事需不需要追蹤」**只有做事的人知道**:

```
你問:「現在幾點?」          → 對方直接回你一句話。開工單是多餘的。
你問:「幫我分析這 300 頁」   → 對方開工單。因為它要做很久,你會想問進度。
```

**你在送出的當下,並不知道對方要做多久。** 所以由對方決定,是唯一合理的分工。

> 這也是「A2A 沒有純聊天」(第 4 章)的另一面:
> **不是所有訊息都會變成工單,但所有訊息都得說清楚自己屬於哪段脈絡。**
> 「要不要追蹤」是選配的;「你是哪件事的一部分」不是。

> ▌**本專案**
> 我們**一律開工單** —— `SendMessage` 進來,我們就建一個 Task,不做「直接回一則訊息」那條路。
>
> 為什麼簡化?因為在我們的系統裡,**會走 A2A 這道門的一定是「要交辦的事」**;
> 純聊天走的是另一道門(`/api/rooms/.../messages`),那道門根本不碰協定層。
> 兩道門各自單純,好過一道門裡有兩種行為。

### 狀態:一件事會經過哪些階段

規格定義了八種狀態。分成三類就好記:

| 類別 | 狀態 | 意思 |
|---|---|---|
| **進行中** | `SUBMITTED` | 交辦出去了,對方還沒開始 |
| | `WORKING` | 對方在做了 |
| **中斷,等你** | `INPUT_REQUIRED` | 做到一半,需要你補資料 |
| | `AUTH_REQUIRED` | 做到一半,需要你給權限 |
| **終態(不會再變)** | `COMPLETED` | 做完了 |
| | `FAILED` | 做不出來 |
| | `CANCELED` | 你喊停了 |
| | `REJECTED` | 對方一開始就不接 |

```
                    ┌──────────────▶ COMPLETED
                    │
  SUBMITTED ──▶ WORKING ──────────▶ FAILED
      │             │
      │             └──────────────▶ CANCELED
      │
      └──────────────────────────────▶(也可以直接跳終態)

           INPUT_REQUIRED / AUTH_REQUIRED
           ↑ 從進行中「暫停」,補完資料再回去
```

**★ 終態的意思是「不會再變」。** 一件事 `COMPLETED` 之後不會又變回 `WORKING` ——
這讓查詢的人可以安心:**看到終態就可以收工,不用再問第二次。**

**★★ `INPUT_REQUIRED` 是 agent 跟工具最大的差別**

回想第 2 章那張 MCP vs A2A 的對照表:「差別在於對方有沒有自主性」。

**工具不會問你問題。** 你呼叫一個查天氣的 API,它要嘛給你天氣、要嘛報錯,
它不會說「請問你要攝氏還華氏?」

**agent 會。** 而 `INPUT_REQUIRED` 就是協定裡專門給這件事的位置 ——
就是修車廠打電話來問「煞車皮要不要換」的那一刻。

> ▌**本專案**
> 我們的狀態機**只實作了七條轉換**,而且沒有任何一條通往 `INPUT_REQUIRED`:
>
> ```
> SUBMITTED → WORKING / COMPLETED / FAILED / CANCELED
> WORKING   → COMPLETED / FAILED / CANCELED
> ```
>
> `REJECTED` 與 `INPUT_REQUIRED` **沒有啟用**,原因很實際:它們需要 agent 能夠
> **在回覆裡標記「我需要更多資訊」**,而我們現在的 agent 回覆就是一段純文字,
> 沒有那個標記的位置。
>
> 程式碼裡留了處理 `INTERRUPTED` 的分支,而且旁邊註明**那不是死碼**,
> 是等「agent 能標記」那天到來時,只要在轉換表加一列就會啟用。
> —— 這也是為什麼那張轉換表被寫成一份**宣告式的表**,而不是散在程式碼裡的 if:
> **要擴充的地方集中在一處,比散在七個地方好。**

### contextId 是什麼?案件編號

一件事常常不只一張工單。

修車的例子:你的車進廠一次,可能開了三張工單(引擎、煞車、烤漆)。
它們是**三件獨立的事**,但屬於**同一次進廠**。

- `taskId` = **工單號**。一張工單一個號。
- `contextId` = **案件編號**。同一段合作裡的所有工單、所有訊息,共用一個。

**為什麼需要它?** 因為 agent 需要知道「這句話跟剛才那件事有沒有關係」。
沒有 contextId 的話,每一則訊息都是孤兒 —— 對方無法把前後文串起來。

> ▌**本專案**
> 我們的 `contextId` **直接就是房間名**(例如 `main`)。
> 同一個房間裡的所有訊息與任務,自然屬於同一段脈絡。
>
> 這個對映不是巧合 —— 我們是先做了聊天室,後來才發現「房間」跟 `contextId`
> 講的是同一件事。(那段故事在 `doc/TUTORIAL.md` 第 5 章。)

### 一句話收束

> **一個協定有幾個動詞,就洩漏它認為什麼事情難。**
> A2A 七個動詞裡三個在問進度,兩個在送話 ——
> 它認定的難題不是「怎麼把事情交出去」,而是「**交出去之後,你怎麼知道它還活著**」。

## 第 6 章:一次完整的交辦,以及等待的三種姿勢

前五章都在講零件:名片、訊息、工單、狀態、脈絡。這一章把它們串起來走一遍。

### 完整的一趟:從不認識到結案

假設 alice 要交辦一件事給 bob。

```
 ①  alice 讀 bob 的名片                        ← 第 3 章
     GET /agents/bob/.well-known/agent-card.json
     知道了:要打哪個網址、用 JSON-RPC、他支援串流但不支援回呼

 ②  alice 送出交辦
     POST /agents/bob/a2a   method: SendMessage
     ────────────────────────────────────────────
     bob 這邊建立一張工單,狀態 = SUBMITTED
     alice 拿到工單號(taskId)

 ③  bob 收到通知,開始做
     ────────────────────────────────────────────
     狀態 = WORKING

 ④  bob 做完,回報結果
     ────────────────────────────────────────────
     狀態 = COMPLETED
     結果包成一則 Message,放進工單的 history

 ⑤  alice 知道結案了
     —— 怎麼知道?那就是「等待的三種姿勢」,見下一節
```

**這五步裡,只有 ①②⑤ 是協定規定的。③④ 那兩個箭頭——「bob 怎麼被通知」與
「bob 怎麼回報」——規格一個字都沒說。** 下一章(第 7 章)會專門講這件事。

> ▌**本專案**
> 我們把 ③④ 那兩個空缺這樣填:
>
> ```
> ③ 怎麼通知 bob      工單一建立,聊天室就長出一則訊息,而且【強制在裡面點名 bob】——
>                     我們的聊天室會解析每則訊息裡的 @某人,存成一個 mentions 欄位;
>                     建工單時系統會硬把目標的名字塞進去,即使交辦的人沒打那個 @。
>                     bob 的敲鈴器看到有新訊息就敲他,而 bob 醒來看到自己被點名,才知道這則是給他的。
> ③ 怎麼判定「開始了」  bob 醒來撈訊息時會帶上自己的名字(reader=bob);
>                     hub 看到「目標本人撈到了那則」就把狀態推成 WORKING
> ④ 怎麼判定「做完了」  bob 回覆那則訊息(reply_to 指向它);
>                     hub 看到「目標本人回覆了」就推成 COMPLETED
> ```
>
> ★ **這三條全部是我們發明的**,規格裡沒有 `reader=`、沒有 `reply_to`、沒有敲鈴器。
>   規格只說「工單要有狀態、狀態要能查」,**至於什麼時候該變狀態,它交給實作決定**。
>
> 所以你去看別人的 A2A 實作,會看到完全不同的判定方式 —— 那不是他們做錯,
> 也不是我們做錯,是**那一格本來就是空的**。

### 等待的三種姿勢

交辦出去之後,你怎麼知道它好了?A2A 給了三種選擇,而**它們的差別不在方便,在你的處境**。

#### 姿勢一:阻塞 —— 站在那裡等

```
SendMessage(configuration: { returnImmediately: false })
     │
     └──▶ 這個請求【不會馬上回來】,它會一直掛著,直到工單進終態
```

**像什麼**:你打電話給對方,然後**不掛電話**,一直等他辦完。

**適合**:很快就好的事;或者你寫的是一段同步的程式碼,只想要一個結果。

**代價**:你的程式在這段時間裡**卡住了**。對方做十分鐘,你就掛十分鐘。

#### 姿勢二:串流 —— 邊做邊聽

```
SendStreamingMessage
     │
     └──▶ 一條會持續吐東西的連線:先給你工單,然後每次狀態變了就推一則
```

**像什麼**:你打電話過去,對方一邊做一邊跟你講「找到零件了」「開始裝了」「好了」。

**適合**:你想看進度、想給使用者一個進度條。

**代價**:連線要一直開著。斷了就要重連。

#### 姿勢三:回呼 —— 你留個電話,好了叫我

```
你先跟對方講好一個網址,對方做完之後【主動打過來】
```

**像什麼**:你留下電話就走,對方辦完打給你。

**適合**:要做很久的事。你不用掛著,對方也不用一直被問。

**★ 代價是這三種裡最硬的:你必須有一個「對方打得到」的網址。**

如果你在自己的筆電上、在公司的內網後面、在一個沒有固定 IP 的地方 ——
**對方根本打不進來。** 這不是設定問題,是網路拓撲問題。

> ▌**本專案**
> 我們**不支援回呼**,而且在名片裡誠實寫著 `"pushNotifications": false`(第 3 章)。
> 別人如果硬要用,會拿到一個明確的錯誤碼,而不是石沉大海。
>
> **為什麼不需要**:我們的 agent 跑在使用者自己的電腦上,外面打不進來 ——
> 正好就是上面說的那個拓撲問題。
>
> 但我們不需要它,是因為**那個需求被另一個東西滿足了**:敲鈴器(bell)。
> 它在本機側盯著伺服器的直播,有事就敲醒 agent。
> **效果跟回呼一樣(有事才動),但方向相反 —— 不是外面打進來,是裡面自己去聽。**
>
> ★ 這是一個值得記的模式:**當「別人打不進來」時,把連線的方向反過來。**
> 這在網路上是老招 —— 你的瀏覽器也是這樣收即時通知的。

#### ▌我們自己的鐵則:agent 派任務一律用「不等待」

> ▌**本專案**
> 我們的 `AGENTS.md` 有一條規矩:**agent 之間互派任務,一律 `returnImmediately: true`。**
>
> 為什麼?因為我們的 agent 是「**被叫醒 → 讀訊息 → 回一則 → 睡回去**」的迴圈。
> 如果它派任務時選了阻塞,它就**卡在那一回合裡**,連自己的鈴聲都收不到 —— 整個死掉。
>
> 而它不需要阻塞:**對方回覆時會流進聊天室,而聊天室會敲醒它。**
> 換句話說,我們用「敲鈴器」這個第三方,把「等待」變成了「被通知」。
>
> (阻塞模式我們有留著,那是給**外部 client** 用的 —— 一段跑在別處的同步程式碼。)

### ★ 三種姿勢真正的分界

初學者容易以為這是「效能取捨」——哪個比較快、哪個比較省。**不是。**

```
你能不能用【回呼】     取決於:對方打不打得到你          ← 網路拓撲
你能不能用【阻塞】     取決於:你卡住的時候會不會出事    ← 你的程式結構
你會不會用【串流】     取決於:你需不需要看到中間過程    ← 產品需求
```

**三個問題,三種答案,沒有一個跟「哪個比較好」有關。**

### 一句話收束

> **等待的姿勢不是喜好問題,是處境問題。**
> 一個協定給你三種等法,不是因為它猶豫不決,是因為
> **它知道自己不會知道你在什麼樣的網路裡、寫著什麼樣的程式。**

## 第 7 章:它刻意不管的四件事

前面六章都在講 A2A **管什麼**。這一章講它**不管什麼** —— 而這份清單比你以為的長,
**而且那正是它能被那麼多人用的原因。**

這也是讀者問的第一個問題的另一半答案:**「A2A 到底處理哪一段?」**

### 先講為什麼一個協定要刻意不管事

**每多管一件事,就多一種「你的環境跟我假設的不一樣」的失敗。**

想想 USB:它規定插頭的形狀、電壓、資料怎麼傳。**但它完全不規定你的隨身碟裡面
用什麼晶片、你的滑鼠怎麼算游標位置。** 如果 USB 當初連這些都規定了,
今天就不會有 USB 麥克風、USB 網卡、USB 風扇 —— 那些用途發明的時候,USB 早就定案了。

**一個協定管得越少,能接上它的東西就越多。** 代價是:那些沒被規定的事,
每個人都得自己解決,而且**大家的解法會不一樣**。

下面四件事,就是 A2A 留白的地方。

### 空缺一:怎麼知道「有哪些 agent 存在」

第 3 章講了名片:**只要你知道網址,就能認識一個 agent。**

**但你怎麼知道那個網址?**

A2A 對此**沒有規定**。它解決的是「認識」,不是「發現」。

生活裡的對照很清楚:知道電話號碼就能打給對方(那是電話協定管的),
**但「電話簿」不是電話協定的一部分** —— 它是另外一個東西,而且有很多種:
114 查號台、Google 搜尋、朋友給你的名片。

> ▌**本專案**
> 我們自己加了一個 `GET /agents`,列出現在連著線的 agent。
> **那不是規格的一部分**,`doc/A2A_MAPPING.md` 裡明白標著「非 spec,方便探索」。
>
> 業界填這一格的方式各不相同:有人做註冊中心(registry)、有人做目錄服務、
> 有人乾脆把網址寫死在設定檔裡。**都合法,因為那一格是空的。**

### 空缺二:怎麼叫醒對方

規格假設的是:**對方是一台一直開著、隨時能接請求的伺服器。**

**但很多 agent 不是。** 它可能是你電腦上的一個 CLI 程式、一個桌面應用、
一個平常關著、要用才開的東西。**你沒辦法「打進去」,因為它根本沒在聽。**

規格對這件事一個字都沒說 —— 它假設你已經解決了。

> ▌**本專案**
> 這正是我們整個專案最初的問題(`doc/TUTORIAL.md` 第 1 章就在講它)。
> 我們的解法是**敲鈴器**:一個廉價的小程式在本機側盯著伺服器的直播,
> 有新訊息就把一行字敲進 agent 的輸入框。
>
> 第 6 章講過這個模式:**當「別人打不進來」時,把連線的方向反過來。**

### 空缺三:對方內部怎麼把事情做完

協定管到**工單**為止。工單怎麼被執行,它不看。

對方可能是:

- 一個大語言模型
- 一套寫死的規則引擎
- **後面坐著一個真人**,收到工單就自己動手做

**協定不知道,也不在乎。** 它只要求「狀態要正確反映進度」。

★ **這是刻意的,而且價值很大**:它讓「換掉裡面的實作」**不影響任何 client**。
今天用 A 模型、明天換 B 模型、後天改成人工處理 —— 對交辦方來說完全一樣。

> ▌**本專案**
> 我們的 agent 後面是 Claude Code 或 Codex,**而協定層從頭到尾不知道這件事**。
> `a2a.py` 裡沒有任何一行提到「模型」——它只知道有一個叫 bob 的東西,
> 而那個東西會回覆訊息。

### 空缺四:誰有資格叫誰做事

這一格最容易被誤會,因為 A2A **有**講認證。

名片裡可以宣告 `securitySchemes` —— 「跟我說話要帶什麼鑰匙」。
所以協定確實給了「**你怎麼證明你是誰**」的位置。

**但它沒給「誰可以做什麼」的規則。**

這兩件事的差別是:

| | 問題 | 誰管 |
|---|---|---|
| **認證** authentication | 你是誰? | 協定有給位置 |
| **授權** authorization | 你可以做這件事嗎? | **協定不管** |

**後果是:每一個實作都得自己列一張「哪些動作要保護」的清單。** 而列清單就會漏。

> ▌**本專案**
> 我們就漏了一個,而且是**在寫這份教學之前才發現的**:
>
> 我們的認證只掛在「送訊息」那兩個動詞上,而 **`CancelTask` 會改變狀態卻不在清單裡** ——
> 意思是開啟認證之後,任何人只要知道一個工單號,不用鑰匙就能取消別人的任務。
>
> 現在沒出事,因為認證預設是關的、而且只在區網跑。程式碼旁邊釘了一句
> 「開啟認證上線前必修」,`doc/A2A_MAPPING.md` 也記了一筆。
>
> ★ **把這個洞寫進教學裡,比藏起來有用**:它示範了這一格是空的所帶來的實際風險 ——
>   **不是「我們比較不小心」,是「每個自己列清單的人都會漏」。**

### ★ 這四格的共同點

回頭看這四件事,你會發現它們有一個共同的形狀:

```
    A2A 規定的       ┃  留白的
    ───────────────────────────────────────
    怎麼認識一個 agent ┃  怎麼發現有哪些 agent
    怎麼交辦、怎麼追蹤 ┃  怎麼叫醒對方
    工單長什麼樣       ┃  工單怎麼被執行
    怎麼證明你是誰     ┃  誰可以做什麼
```

**左邊全部是「兩方之間的約定」;右邊全部是「你自己那一側的事」。**

這條線畫得很一致:**凡是只有你知道的事(你的網路長怎樣、你的 agent 怎麼跑、
你的組織誰能做什麼),協定一律不碰。**

因為它一碰,就會碰錯。

### 一句話收束

> **一個協定的價值,一半在它規定了什麼,一半在它拒絕規定什麼。**
>
> 規定得越多,能用它的人越少。A2A 之所以能讓 Google 的 agent 跟你筆電上那個
> CLI 講上話,**正是因為它對「你的筆電是什麼樣子」一無所知,而且它知道自己不知道。**

## 第 8 章:多 agent 系統的三種形狀,以及 A2A 在哪裡登場

這一章回答的是:**一般的多 agent 架構,到底怎麼「用」A2A?**

答案有點反直覺,所以我們先看形狀,最後再回答。

### 三種形狀

多個 agent 要一起做事,組織方式大致是這三種。**用公司來想最快。**

#### 形狀一:中心調度 —— 一個總管配一群專才

```
              ┌──────────┐
              │   總管    │
              └────┬─────┘
         ┌─────────┼─────────┐
         ▼         ▼         ▼
      ┌─────┐  ┌─────┐  ┌─────┐
      │查資料│  │寫程式│  │做簡報│
      └─────┘  └─────┘  └─────┘
```

**總管拿到需求,拆成小塊,分給專才,收回結果,組裝成答案。**
專才之間**不互相講話** —— 它們只認識總管。

- **誰是 client**:總管(它提出要求)
- **誰是 server**:每個專才

**優點**:好控制、好追蹤。所有決策都在一個地方,出事知道找誰。
**缺點**:總管是瓶頸,也是單點故障。而且它得懂每個專才會什麼。

#### 形狀二:對等接力 —— 沒有總管,誰接到誰處理

```
      ┌─────┐        ┌─────┐        ┌─────┐
      │  A  │───────▶│  B  │───────▶│  C  │
      └─────┘        └─────┘        └──┬──┘
         ▲                              │
         └──────────────────────────────┘
```

**沒有人統籌。** 每個 agent 做完自己那段,決定「接下來該誰」,把棒子交出去。

- **誰是 client / server**:**兩種都是,而且一直在換** —— 這就是第 1 章那個服務生。

**優點**:沒有瓶頸,加一個成員不用改總管。
**缺點**:**沒有人知道全局。** 事情做到哪了、會不會繞圈、誰該收尾,都要另外想辦法。

#### 形狀三:階層 —— 總管底下還有總管

```
                    ┌────────┐
                    │ 大總管  │
                    └───┬────┘
              ┌─────────┴─────────┐
         ┌────▼────┐         ┌────▼────┐
         │ 組長 A   │         │ 組長 B   │
         └────┬────┘         └────┬────┘
          ┌───┴───┐           ┌───┴───┐
          ▼       ▼           ▼       ▼
        專才    專才         專才    專才
```

就是形狀一的遞迴:**一個專才,本身可以是另一組人的總管。**

- **關鍵性質**:對大總管來說,組長 A 就是一個普通的 server ——
  **它不需要知道組長底下還有人。**

**優點**:能長大。每一層只需要認識自己下面那層。
**缺點**:一件事要穿過好幾層,慢,而且出錯時難追。

> **這三種形狀不是 A2A 發明的**,它是所有「多個東西一起做事」的系統都會遇到的分類 ——
> 公司組織、微服務、作業系統的行程,全都在這三種之間選。

### ★★ 現在回答那個問題:架構「怎麼用」A2A?

**這是這一章最重要的一段,而它的答案是反直覺的:**

> **這三種形狀,跟 A2A 沒有必然關係。你可以一種形狀都不用 A2A。**

看一個真實的例子(2026-07-28 查證):

**LangGraph** 有一個官方的 `langgraph-supervisor` 套件,做的就是**形狀一**:
一個 supervisor 用 LLM 判斷該把子任務交給哪個 agent,收回結果再決定下一步。
**Google 的 ADK** 則以**形狀三**(agent 團隊、明確角色與委派)為原生強項。

**但那些 agent 之間的呼叫,大多發生在同一個程式裡** —— 它們是函式呼叫,
是同一個行程裡的物件互相呼叫。**那裡面一行 A2A 都沒有,也不需要有。**

#### 那 A2A 什麼時候登場?

**當一條邊跨出去的時候。**

```
   同一個程式裡           跨出去了
   ──────────────────────────────────────────
   函式呼叫              → 需要協定
   同一份記憶體           → 需要序列化
   同一個作者             → 需要事先講好格式
   你控制兩端             → 你只控制一端
```

所以正確的問法不是「**我要用哪種架構**」,而是:

> **我的架構裡,哪幾條邊跨出了我的邊界?**

同一個「形狀一」,可以有兩種完全不同的部署:

```
  (A) 全部在我的程式裡
      總管 ──函式呼叫──▶ 專才1  專才2  專才3          ← 零 A2A

  (B) 有一個專才是別人家的
      總管 ──函式呼叫──▶ 專才1  專才2
           ──── A2A ───▶ 別人公司的專才3              ← 這條邊需要 A2A
```

**架構一樣,而 A2A 只出現在 (B) 那一條線上。**

> **這就是為什麼 A2A 要那麼克制**(第 7 章)。它不知道你的架構是什麼形狀,
> 也不需要知道 —— 它只負責**那一條跨界的邊**上,兩邊怎麼講話。

#### ★ 連 A2A 的作者自己都是這樣用的

上面那張 (B) 圖不是我們推想出來的形狀 —— **它是 Google 官方框架的實際做法。**

A2A 由 Google 發起,而 Google 自家的 agent 框架 **ADK** 預設是行程內的階層委派
(`sub_agents`)。**當某個成員在別人家時**,它才換一種掛法(2026-07-28 查官方文件):

```python
# 把「別人家的 agent」掛成自己的一個成員 —— 用名片網址指過去
from google.adk.agents.remote_a2a_agent import RemoteA2aAgent

prime_agent = RemoteA2aAgent(
    name="prime_agent",
    description="Agent that handles checking if numbers are prime.",
    agent_card="http://localhost:8001/a2a/check_prime_agent/.well-known/agent-card.json",
)
```

```python
# 反過來:把自己包成一台 A2A server,讓別人掛
from google.adk.a2a.utils.agent_to_a2a import to_a2a

a2a_app = to_a2a(root_agent, port=8001)
```

**注意第一段的 `agent_card` 參數 —— 那就是第 3 章那張名片,而且路徑正是 `.well-known`。**
理論在這裡跟實務接上了。

★ 這件事的份量在於:**推 A2A 的人,自己的框架預設也不用 A2A。**
不是因為他們不信任自己的協定,而是因為**同一個程式裡用協定沒有意義** ——
協定要解的是跨界,而那條界線在自家程式裡不存在。

### 那我什麼時候會需要它?

三個訊號,任何一個成立就值得考慮:

1. **對方不是你寫的** —— 你們不會有機會坐下來講好一套私有格式
2. **對方不在你的程式裡** —— 已經要序列化了,那不如用個標準格式
3. **對方將來可能被換掉** —— 有標準介面,換掉時 client 不用改

反過來,如果三個都不成立(全是你寫的、跑在同一個程式裡、不會換),
**用 A2A 只是給自己找事** —— 直接呼叫函式又快又好除錯。

> ▌**本專案**
> 我們是**形狀二(對等接力)**,而且是一個少見的極端:**每一條邊都跨界。**
>
> 每個 agent 是一個獨立的行程,跑在自己的終端機視窗裡(甚至可能在別台電腦上)。
> 它們之間沒有任何「同一個程式裡的函式呼叫」可用 —— 所以每一次交辦都得走協定。
>
> **這是刻意的**:目標本來就是「不同產品的 agent(Claude Code、Codex)能一起工作」,
> 而那意味著我們沒有「大家都在同一個程式裡」這個選項。
>
> ★ 也因此,我們對 A2A 的用法**不能當成典型**。
>   多數人用 A2A 只在少數幾條邊上,而我們是全部 —— **我們是三分之一裡的極端案例,
>   不是標準用法。**

### 一句話收束

> **架構決定形狀,邊界決定協定。**
>
> 「要不要用 A2A」不是架構問題,是**地理問題** ——
> 你只需要在「你的世界結束、別人的世界開始」的那條線上用它。
> 線的裡面,你想怎麼叫都可以。

## 第 9 章:動手 —— 對著自己那台 hub 走一次

前面八章都是紙上談兵。這一章你要真的打指令。

**這份教學相對其他教學的優勢就在這裡:你桌上就跑著一台 A2A 伺服器。**
不用註冊、不用申請 API key、不用假裝有一個遠端 agent。

### 開始之前

確認 hub 跑著(視窗一是 `hub.bat`),而且至少有一個 agent 連著線
(視窗二是 `uv run bell.py --name alice -- claude -r`)。

> ⚠️ **下面所有輸出裡的編號、時間、id 都會跟你看到的不一樣。**
> 那是正常的 —— 訊息編號會一直往前跑,任務 id 是隨機產生的。
> **看「形狀」對不對,不要對數字。**
>
> 下面的紀錄是 2026-07-28 在一台跑了兩天的 hub 上實際跑出來的。

---

### 第一步:看一張名片(對應第 3 章)

```bash
curl -s http://127.0.0.1:8787/agents/alice/.well-known/agent-card.json
```

你會看到第 3 章那張 JSON。**先確認一件事**:裡面
`supportedInterfaces[0].url` 那個網址,就是下一步要打的地方。

**這一步是所有 A2A 互動的起點** —— 你不需要事先知道端點,名片會告訴你。

---

### 第二步:看看現在有誰在線

```bash
curl -s http://127.0.0.1:8787/agents
```

> ▌**本專案**
> 提醒一次(第 7 章的空缺一):**這個端點不是 A2A 規格的一部分**,是我們自己加的。
> 規格解決「知道網址之後怎麼認識他」,不解決「怎麼知道有誰存在」。

---

### 第三步:真的派一個任務出去

**注意 `senderKind`(第 4 章)與 `returnImmediately`(第 6 章)兩個欄位。**
目標我們用 `alice` —— 派給自己最不打擾別人,而流程完全一樣。

```bash
curl -s -X POST http://127.0.0.1:8787/agents/alice/a2a   -H "Content-Type: application/json"   --data-binary @- <<'EOF'
{"jsonrpc": "2.0", "id": 1, "method": "SendMessage", "params": {
  "message": {
    "role": "ROLE_USER",
    "parts": [{"text": "教學示範用的任務:請回一句「收到」就好"}],
    "messageId": "隨便一個唯一字串",
    "contextId": "main"
  },
  "configuration": {"returnImmediately": true},
  "metadata": {"senderName": "alice", "senderKind": "agent", "deadlineSeconds": 600}
}}
EOF
```

**實際回來的東西**:

```json
{
  "id": "5772fc5324d04e1caec78c81c4d4eaa1",
  "contextId": "main",
  "status": {
    "state": "TASK_STATE_SUBMITTED",
    "timestamp": "2026-07-28T10:07:02+00:00"
  }
}
```

**把那個 `id` 記下來** —— 那是工單號(第 5 章),接下來都要用它。

> 這時候去看瀏覽器上的聊天室,你會看到多出一則訊息,旁邊掛著 **TASK 徽章**,
> 而且它自動 `@` 了目標 —— **那個 @ 不是誰打的,是工單長出來的**(第 6 章的橋接③)。
> 因果是反過來的:**先有 Task,才有那個 @**,而不是「@ 了誰就變成 Task」。

---

### 第四步:查狀態 —— 這是本章的重點

```bash
curl -s -X POST http://127.0.0.1:8787/agents/alice/a2a   -H "Content-Type: application/json"   -d '{"jsonrpc":"2.0","id":1,"method":"GetTask","params":{"id":"你剛剛那個 id"}}'
```

**剛建完馬上查:**

```
state = TASK_STATE_SUBMITTED
```

**接著讓目標「讀到」那則訊息** —— 也就是第 6 章那條我們自己發明的橋接:

```bash
curl -s "http://127.0.0.1:8787/api/rooms/main/messages?since_id=0&reader=alice"
```

**再查一次:**

```
state = TASK_STATE_WORKING
```

★ **停在這裡看一眼。** 你剛剛只是「撈了一批訊息」,而任務的狀態**自己前進了一格**。

那就是第 6 章講的:**我們把「撈訊息」當成已讀回條。**
規格沒有規定這件事,是我們填的空缺 —— 別人的實作可能用完全不同的方式判定。

---

### 第五步:讓它結案

目標回覆**那則任務訊息本身**(`reply_to` 指向它):

```bash
curl -s -X POST http://127.0.0.1:8787/api/rooms/main/messages   -H "Content-Type: application/json"   --data-binary @- <<'EOF'
{"from": "alice", "kind": "agent",
 "text": "收到", "reply_to": 那則任務訊息的編號}
EOF
```

**再查一次狀態:**

```
state   = TASK_STATE_COMPLETED
history 有 2 則
最後一則的 role = ROLE_AGENT
最後一則的文字 = 收到(這是 A2A_TUTORIAL 第 9 章的示範任務)
```

**你剛剛完整走過了一次 A2A 的任務生命週期。**

★ 注意 `history` 那兩則:**第一則是交辦(`ROLE_USER`),第二則是回覆(`ROLE_AGENT`)。**
那就是第 4 章的 `role` —— **同一個 alice,兩則訊息裡是兩個角色**,
因為她這次自己派給自己(第 1 章:client 與 server 會互換,這是最極端的示範)。

---

### 第六步:看整份工單

```bash
curl -s http://127.0.0.1:8787/api/rooms/main/tasks
```

或在瀏覽器點那則訊息旁邊的 **TASK 徽章** —— 會跳出視窗顯示完整的生命週期。

> ▌**本專案**
> 那個視窗背後打的是 `GetTask`,跟你剛剛用 curl 打的是同一個東西。
> **UI 沒有任何魔法,它只是把指令包成一顆按鈕。**

---

### 如果哪一步卡住了

| 症狀 | 多半是 |
|---|---|
| `agent not online` | 目標的敲鈴器沒開。名冊是「現在誰連著線」(第 7 章空缺一) |
| 狀態一直停在 `SUBMITTED` | 目標沒有帶 `reader=` 去撈訊息 —— 已讀回條沒觸發 |
| 狀態變成 `FAILED` | 逾時了。`deadlineSeconds` 預設 300 秒 |
| 回覆了但狀態沒變 | `reply_to` 指錯訊息了,要指**任務訊息本身**,不是最近那一則 |
| 中文 JSON 出現亂碼或 parse error | Windows 上要走 stdin(上面那種 `<<'EOF'` 寫法),不要放進 `-d '...'` |

### 一句話收束

> **讀十遍不如打一次。**
>
> 這一章沒有教任何新觀念 —— 每一步都是前八章講過的東西。
> 但你剛剛看到 `SUBMITTED` 自己變成 `WORKING`,那一刻的理解
> **跟讀到「已讀回條會推進狀態」那句話時,不是同一種理解。**
