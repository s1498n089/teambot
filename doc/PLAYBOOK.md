## 一、判斷類:這個該不該改

### 1. 對外說謊 > 對內說謊

**註解錯了,誤導的是下一個改程式的人;UI 上的字錯了,是直接對使用者說謊。**

掃描時 **UI 字串的優先級高於註解**。使用者看到一句話會照著它推論,而他沒有辦法查證。

> 實例:任務徽章的滑鼠提示寫著「伺服器重開之前的任務,狀態已經沒了」。
> 任務持久化上線之後,重開會從檔案復原 —— 看到那句話的人會推論「那我不要重開就好」,
> 而那個推論是錯的。真正的原因是那則訊息比持久化功能還老。

### 2. 常數區該集中的是「政策」,不是「參數」

- **政策** = 產品決定,通常在別的地方也有一份對應物(對齊伺服器的白名單、與 CSS 綁定的字級範圍)。**該集中。**
- **參數** = 某一段程式的局部手感,離開使用它的那幾行就沒有意義(捲動判定的 120 / 40 / 60 像素)。**該留在原地。**

集中是為了讓「為什麼是這個數字」有地方回答,不是為了讓常數區變長。

### 3. 測試資料要中性,歷史敘述要具名 —— 位置決定去留

同一個退役成員的名字,出現在兩個地方要有兩種處置:

- 在**測試資料**裡(`KNOWN = {"alice", "bob", "dev"}`)→ 換成中性名字。
  一份長得像名冊的測試資料,會讓讀者分不清「那是資料」還是「那是名冊」。
- 在**歷史敘述**裡(「這正是 dev 問題的解法」)→ 留著。
  歷史用真名才有意義。

### 4. 零使用點的東西是空殼,刪它不是「砍功能」

「砍功能」的界線是**有人在用的能力消失**。一個從來沒有被引用過的例外類別、常數、
CSS class,刪掉不改變系統的任何行為。

留著它等於留一個「將來也許會用到」的空殼 —— 而那正是 `dev` 與邀請碼的下場。

**但是**:刪掉一個名字之後,要 **grep 那個名字**,不只是 grep 它的使用點。
使用點是程式碼,引用是註解,而**註解不會編譯失敗**。

### 5. 刪死碼不用問;關掉需求方點名要的東西必須問

**授權的邊界是他的明示偏好。**

- 沒人用的東西 → 直接刪。
- 他點名要過、後來被關掉或沒做的東西 → 列出來問,不主動改回,也不主動維持現狀。

### 6. 一致性在「模式會被複製的地方」等於正確性

「不硬修」擋的是**淨值為零**的改動(換湯不換藥)。但如果那段程式是**會被下一個人照抄的模板**,
一致性就有淨值:六種區塊六個長得一樣的判斷句,給下一個加第七種的人一個明確樣板;
五個一樣加一個特例,他每次都得猜哪個才是正統。

### 7. 「相對操作」與「絕對操作」

修邊界、修狀態時,優先選**冪等**的寫法:

```
翻轉(相對):point.vx = point.vx * -1        界外時每格翻一次 → 永遠震盪回不來
設方向(絕對):point.vx = Math.abs(point.vx)  套幾次結果都一樣 → 一定收斂
```

### 8. 副本可以存在,但要指名正本

同一個值/規則在多處出現,不見得要合併(合併的漣漪可能比重複更貴)。
但**每一份副本都要指名正本**,而且要寫明**只改一邊的後果**。

> 後果比互指高一級 —— 後果才是讓人不敢只改一邊的東西。

### 9. 有意識的選擇,跟沒想過,在程式碼上長得一模一樣

所以「決定不做某件事」要寫下來,而且要寫三段:**是有意識的選擇、為什麼可接受、
什麼情況下要回頭處理。**

### 10. 遷移只能改變「資料存在哪裡」,不能順便改變「資料是什麼」

補欄位、加版本標記這類**格式**升級,不算竄改歷史 —— 前提是**內容一個字都不變**。
補全的規則要跟原本讀取端的邏輯一字不差,先備份、改完比對筆數。

**趁遷移偷改語意是最難追查的一種資料損壞**:兩件事混在同一次改動裡,
事後沒有人分得出來哪個結果是哪一邊造成的。

> 相關的反面:讀取時修補格式,會讓**記憶體與檔案分岔**,
> 而那個分岔通常不寫在任何地方 —— 下一個直接讀檔案的人
> (備份腳本、資料分析、另一個實作)會拿到跟 API 不一樣的東西,而且不知道為什麼。
> 修補屬於**遷移**(做一次、寫進檔案),不屬於**讀取**(每次都做、只留在記憶體)。

### 11. 自己寫還是用套件 —— 那把尺原本少了一個維度

**原本的尺**:「格式自己寫、協定用庫」。
`.env` 是一種**格式**,規則簡單、不會演進,十幾行就寫完;
而 HTTP、A2A 那種**協定**會持續改版,追規格不是我們的差異化,才該外包。

那把尺自己還寫了退場條件:「哪天真的需要引號跳脫、多行值、`${VAR}` 展開,就是該換的時候。」

**2026-07-28 被需求方推翻,理由是那把尺漏了的維度:**

> 「能不要自己寫就不要自己寫。裝一個套件對開發者無感,
>   重點是現成好用就好,**而且查資源超方便**。」

**★ 「查得到答案」本身就是一種功能,而那是自己寫的東西永遠給不了的。**

- 搜尋「python dotenv 怎麼寫引號」→ 一百篇答案
- 搜尋「這個專案的 envfile.py 怎麼寫引號」→ 零篇

而且自己寫的東西會**默默地少支援一堆寫法**,使用者不會知道 ——
他只會發現「我寫的設定沒生效」,然後開始懷疑自己。

**修正後的尺**:自己寫的成本不只是「行數」與「日後維護」,還有
**使用者卡住時查不查得到答案**。十幾行的解析器在第一項上贏,在第三項上輸得很徹底。

> **這條的最終擁有者是需求方,不是寫 code 的人。** 引不引入依賴帶有主觀成分
> (無感 vs 有感、方便 vs 潔癖),而承擔後果的是要長期用它的人。
> 我們當初寫下的退場條件太窄 —— 它只想到「功能不夠用才換」,
> 而他用的是完全另一個維度。**寫下退場條件是好習慣,但別以為自己想得到全部的出口。**

### 12. 換掉一個實作時,「接受新東西的哲學」有前提

換套件時很容易走到另一個極端:「既然用人家的,就整套照人家的方式」。

**前提是那個哲學不違反你自己的契約。** 實例:python-dotenv 遇到沒有等號的行,
會收成 `value=None` 而且**完全不出聲** —— 而「壞行要出聲」正是我們這個模組的契約
(靜默略過會製造它自己警告過的「我明明設了卻沒生效」)。

所以那一層要自己補回來。**補契約不等於重寫實作**:解析仍然全交給套件,
我們只在它回來的結果上多看一眼。

同理,換掉實作之後要重新分配測試:

- 測**解析規則**的(引號、空白、空值)→ 刪掉,那是別人的家務,
  它們抓不到我們的 bug,只會在對方改版時發假警報。
- 測**我們的契約**的(環境變數優先、回報套用了哪些、壞行出聲)→ 留著。
- ★ 特別要留的是**「我們的靈魂剛好依賴對方一個預設值」**那條 ——
  這裡是 `override=False`。對方哪天改預設,我們的靈魂會**無聲**斷掉,
  而那條測試是唯一會叫的東西。

### 13. 文筆好的過時註解,比文筆差的更危險

因為沒有人會懷疑它。

## 二、流程類:兩個人怎麼一起看

### 1. 四拍節奏

**① 兩人各自掃、各自報 → ② 合流定案 → ③ 一人執行 → ④ 另一人審。**

關鍵是 ① **兩人同時掃、報完才看對方的**。先看到對方清單的人會被錨定,
而兩份獨立的清單合起來才有交集與補集。

長檔案(1000 行以上)可以分半各掃一半,**報完再交換複查對方那半** —— 同樣的理由。

### 2. 「照著做會失敗」的內容不排隊

一般項目照四拍走。但如果文件教人去打一個不存在的端點、或給了一個會讓人做錯事的指示,
**當拍就改**,不等合流。

**光刪不補等於把人從「撞牆」改成「沒牆可找」** —— 刪掉錯誤做法的同時要寫上正確做法。

### 3. 矛盾比錯誤糟

錯誤至少方向一致,讀者會一起走錯;**矛盾讓讀者自己擲硬幣**。
同一節裡兩句話互相打架時,優先級高於單純的錯誤。

### 4. 方向可以猜,結論要用查的

從現象推論出來的結論,寫的時候要標明它是推論。
**「工具給了數字就當結論」是同一個病** —— grep 出來的計數要回頭確認它數的是不是同一件事。

### 5. 必要漣漪 vs 提前開工

改 A 檔連帶要動 B 檔時,分兩種:

- **機能性漣漪**:不改 B,A 的修正就不生效(加了參數卻沒有人傳)→ 當拍一起改。
- **一致性漣漪**:同一句話的兩個副本,分開改保證漏一個 → 當拍一起改。

其餘的留給 B 檔自己那一拍。

### 6. 四拍防不了「兩個人用同一個角度看」

四拍防的是「**一個人**沒看到」。它防不了兩個人**用同一個角度**看同一件事。

> 實例:提案「版心 `min(1280px, 100vw - 64px)`」,兩個人都投贊成票。
> 但那個 `- 64px` 是**無條件**的,所以手機從 390px 變成 326px —— 每個窄螢幕都退步 64px。
> 諷刺的是,我們前一分鐘才用「不能有任何檔位比現在差」這條判準否決了另一個提案,
> 卻沒有把同一條判準套在版心上。

**對策不是加第五拍,是把檢查放進第③拍的入場動作:執行者動手前,先把數值逐個列出來。**

```
 390px → 提案  326 / 現況  390  ← 比現在【更窄】
1366px → 提案 1280 / 現況  960     ✓
```

一張表就看得出來。抓到它靠的是習慣,不是想得比較周到 ——
而習慣就是「把檢查做進動作形狀裡」在人身上的版本(見第四節)。

### 7. 抓到一個,先問「同一類還有幾個」

發現一處錯誤時,最省事的反應是修那一處。**但一個錯誤通常不是孤例,是某個習慣的樣本。**

> 實例:審稿抓到一句「第 7 章會看到系統的形狀」指錯章(實際在第 8 章)。
> 修掉它只要三秒 —— 但正確的下一步是**把全篇的章號引用抓出來對一次**,
> 因為「章號位移之後忘了改預告」這個成因,不會只發生一次。
> (稽核結果:另外四十幾處都對,但那個「都對」是查出來的,不是猜的。)

**同一個習慣的其他樣本,通常就在你剛才沒看的那幾行裡。**
問「還有幾個」花的時間,幾乎總是比「下次再被抓到」便宜。

### 8. 驗證的空白要說出來

「這支我沒有用瀏覽器看過,驗證停在邏輯層」—— 說出來,對方才補得上。
如果只寫「已驗證」,那一格就永遠是空的,而且沒有人會知道。

## 三、文件類:文件為什麼會爛,以及怎麼寫比較不爛

### 四種腐爛型態(這次遇到的)

1. **死詞散在多檔** —— 一個設計被改掉,講述它的句子平均散在四到六個地方,
   而改的人只會看到自己正在改的那一個。
   > 「伺服器會下發成員顏色」這句話在六個檔案裡各有一份。
2. **跨檔數字失同步** —— 一個檔案裡的數字,描述的是另一個檔案的狀態(章數、測試數)。
   **grep 不到**,因為要找到它得同時知道兩個檔案的狀態。
3. **同檔不同段失同步** —— 同一份文件裡,「講道理的那段」更新了,「查資料的那行」沒有。
   改的人滿腦子在想怎麼把新設計講清楚,清單那行不在視線裡。
   > 這一節自己犯過一次:標題寫「三種」,底下卻多了第四種。
4. **掃描範圍沒涵蓋到的檔案型別** —— 這一輪的死詞掃描 grep 的是
   `*.py` / `*.md` / `*.js`,於是 `server.env.example` 與 `hub.bat` 裡的同一批死詞
   **整批活了下來**,是後來使用者打開檔案才發現的。
   > **列舉檔種時,列舉本身就是漏網的來源。** 對策不是「記得列全」,
   > 而是先跑一次「這個 repo 實際上有哪些副檔名」,拿真的清單去對:
   > ```
   > git ls-files | sed 's/.*\.//' | sort | uniq -c | sort -rn
   > ```
   > 這個專案跑出來有 13 種,而我腦中的清單只有 3 種。

### 對策一:別寫會過期的快照,寫拿到真相的方法

> `uv run pytest # 全套(99 測)` → 這個數字一天內錯了兩次,
> 第二次還是修正者本人造成的。改成「數字會變,跑一次就知道」。

### 對策一之二:更正要下到檔案,不能只到對話

> 實例:我用實測推翻了自己的假設(「表格在窄泡泡裡會橫向捲動」——
> 實際上表格不會捲,它是壓縮欄寬導致每格換行),在聊天室講清楚了,
> **但寫進 `styles.css` 的註解還是舊機制。**

**聊天室裡的更正只有當時在場的人看得到,而註解是留給不在場的人的。**
只更正對話,等於**更正了現在,沒有更正未來**。

這是「講過不等於在產品裡」的完整形:**改過,不等於改進了檔案。**

### 對策二:日期屬於「事件」,不屬於「道理」

- 「2026-07-27 起不再下發顏色」是發生過的變更 → **帶日期 = 資訊**。
- 「點名規則為什麼非得由伺服器下發」是活的道理 → **不帶日期 = 正確**
  (道理不過期,掛日期反而讓它看起來像會過期的快照)。

### 對策三:分清楚需求文件與描述文件

**文件的可信度來自它的身分:**

- **描述文件**(README、對映設計)的義務是**跟上現況**。
- **需求文件**(老闆給的設計依據)的義務是**保存原意**。

改需求書等於竄改當初的要求 ——「我們有沒有做到他要的」這個問題就永遠沒有對照組可查。
正確做法:本體一個字不動,在文末補一節**決策紀錄**(要求什麼 → 做了什麼 → 為什麼),
並在頂部加一行導航,防止讀者把需求當現況。

### 腐爛速度的實測(2026-07-27 當天,同一次體檢)

| 文件 | 性質 | 行數 | 需要修的項目 |
|---|---|---|---|
| `README.md` | 純現況 | 298 | **15** |
| `doc/TUTORIAL.md` 第 0~5 章 | 純道理 | 341 | **3** |
| `doc/ECOSYSTEM.md` | 道理 + 錨定日期的快照 | 277 | **0** |
| `tests/`(六個檔) | 行為規格 | 1256 | **6**(且全部集中在退役機制周圍) |

**文件的腐爛速度是寫法決定的,不是年齡決定的。**

## 四、工具類:規則存在但沒被執行,跟沒有規則的結果一樣

這一天做了三支工具,每一支都是為了同一件事:**把規則做進動作的形狀裡,而不是寫成提醒。**

| 工具 | 為什麼存在(真實的失敗紀錄) |
|---|---|
| `tools/say.py` | 「拿了 last_id 卻沒讀內容」三次(漏看使用者叫停、漏看新成員自我介紹)、「讀完忘了推 cursor」三次、「commit hash 用手打」兩次 |
| `tools/mdtest.js` | 前端唯一的測試被鎖在瀏覽器裡,而「改完記得去按重新整理」靠的是記性 |

**共同的教訓**:每一次犯錯我都寫下了教訓、也說了改法,**然後又犯**。
規則寫了但沒有被執行,結果跟沒有規則一樣。

### ★ 什麼時候「寫在文件裡」就夠?看那條規則的失敗方式

不是每條規則都值得做成工具。判準是:**它被違反的時候,你看不看得出來。**

```
失敗時會【當場報錯】的規則        → 寫在文件裡就夠(下次就記得了)
失敗時【安靜地產生錯結果】的規則  → 必須做進工具,否則永遠抓不到
```

**反面的證據跟正面一樣重要**:這個專案有很多規則從來沒做成工具,也從來沒出過問題 ——
引用不存在的訊息回 422、名字不合法回 422、版本不合印 WARN。
**它們違反時會立刻噴錯,所以「寫在文件裡」就夠了。**

而 2026-07-27 到 28 那九次違反,全部是第二種:

- 只讀了預覽 → 訊息**照樣發出去**,沒人知道我沒讀完
- 反引號被吃 → 訊息**照樣送達**,只是缺了幾個字
- API 回 500 則 → **看起來就是全部**

**失敗的樣子跟成功的樣子長得一模一樣** —— 這種規則靠提醒守不住。

### 退役紀錄:一支工具被另一個習慣取代

`tools/safe_delete.py` 曾經存在(刪程式碼前先列出範圍內有哪些定義),
起因是「用行號範圍刪東西時,連帶吞掉隔壁無關的函式」—— 一小時內發生兩次。

**它在 2026-07-28 退役,不是因為沒用,是因為那個病從源頭消失了**:
改檔的做法後來統一成「**先 `assert` 命中數為 1,再替換**」——
那個做法**根本不用行號**,所以「範圍誤刪」不可能發生。

> ★ **一支工具最好的下場,是它防的問題不再存在。**
>   這時候該砍掉它 —— 留著會讓下一個人以為那個危險還在,然後花時間學一個他用不到的東西。
>   **留教訓,不留檔案。**

### 工具的形狀決定了錯誤會不會被看見

`tools/say.py` 一定會先印出未讀內容才讓你發言 —— 看到了還不讀是人的問題,
但至少不會再出現「我以為我對帳了、其實只取了號碼牌」。

同理,改檔的 patch 腳本一律先 `assert` 命中數為 1。
這一天有兩次把比對字串的縮排抄錯,**兩次都被那個 assert 接住** ——
如果用的是「找到就換、找不到就算了」的寫法,兩次都會是靜默的沒改到,
而我會照樣回報「已完成」。

### 最強的反面證據:同一支工具裡,兩種規則的下場不同

`tools/say.py` 裡有兩條規則:

| 規則 | 做法 | 那一天的下場 |
|---|---|---|
| 發言前要對帳、要看未讀 | **做進形狀**(不做就發不出去) | **零違反** |
| 訊息內容要走 `--file`,不要走 shell 引號 | **寫成說明**(靠記性) | **破功三次** |

同一支工具、同一個人、同一天。**差別只在於規則是被「執行」還是被「提醒」。**

三次破功的順序特別有說服力:第一次之後我寫下教訓;第二次之後我**親手改寫了那段說明**,
把它從「長訊息用」升級成「這是安全問題不是長度問題」;**然後第三次照樣發生。**

> ★ **把提醒寫得更好,不會讓它變成執行。**
>   唯一有效的動作是把它變成「不做就過不去」——
>   第三次之後,`say.py` 改成【收到含反引號的行內文字就直接報錯並指路 --file】。
>   規則從「我會記得」變成「我做不到」,才停下來。

### 規則要寫在正確的理由底下

`tools/say.py` 的 `--file` 選項本來就存在,但說明只寫「長訊息從檔案讀」——
於是它被當成**長度**問題,短訊息就理直氣壯地走了 shell,
然後訊息裡的反引號被當成命令替換執行掉,五個 code 識別字**靜默消失**(不報錯、照樣送出)。

它其實是**安全**問題。規則寫了,但寫在錯誤的理由底下,該用的時候不會被觸發。
