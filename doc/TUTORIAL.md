# 從零讀懂這個專案:一個 A2A Agent 聊天室是怎麼長出來的

> 這份教學給**完全沒背景**的讀者。你不需要先懂 A2A、不需要先懂 agent,
> 只要願意一段一段往下讀 —— 每一段都只用前一段建立的觀念,不會突然冒出術語。
> 真的需要新名詞時,我會先用生活例子解釋,再給它名字。
>
> 讀法建議:配著專案裡的 `server.py`、`a2a.py` 一起看,但先讀完這份再翻 code 也行。

---

## 第 0 章:我們到底在做什麼?

想像一個 LINE 群組,但裡面的成員不是人,是**好幾個 AI**。它們會在群組裡對話、
分工、把任務交辦給彼此;而你(人類)可以在同一個群組裡看它們聊、隨時插話、下指令。

這個專案就是這個群組的「聊天室伺服器」加上「一套讓 AI 們守規矩的規則」。
聽起來很大,但我們會發現它其實是從一個**非常小的問題**長出來的。

先記住一句話,它是整個專案的靈魂,現在看不懂沒關係:

> **「通知只負責叮咚,資料永遠回伺服器撈。」**

這句話到第 3 章你就會完全懂。我們從頭開始。

---

## 第 1 章:一個 AI 怎麼「知道」有人跟它說話?

### 生活類比

你在等一封重要的信。有兩種方式知道信到了:

- **方式 A(輪詢 / polling)**:每 5 分鐘走到信箱看一次。大部分時候白跑,因為信還沒來。
- **方式 B(通知 / push)**:信一到,郵差按你家門鈴。你完全不用跑,聽到鈴才動。

方式 A 很笨但很可靠(信箱不會壞);方式 B 很聰明但需要有人來按鈴(郵差、門鈴都得存在)。

### 這跟 AI 有什麼關係?

一個 AI 助理(以下都叫它 **agent** —— 就是「會自己動手做事的 AI」)平常是**靜止的**:
你問它才答。它不會自己一直醒著等訊息。所以問題來了:

> 群組裡別的成員說話了,一個靜止的 agent 要怎麼「醒過來」看到?

- 如果用**方式 A**:讓 agent 每分鐘醒來查一次「有沒有新訊息」。可行,但**很貴** ——
  對 AI 來說,「醒來查看」這個動作本身要花錢(消耗運算),就算沒有新訊息也照花。
  一天 1440 次,大多是白醒。
- 我們想要**方式 B**:有訊息才叮咚。省錢又即時。

這就是整個專案最初的問題:**怎麼給一個 AI 裝一個門鈴?**

## 第 2 章:最小的聊天室 —— 一個共用的記事本

在解決門鈴之前,先做更基本的:讓大家有地方講話。

### 生活類比

想像一本放在櫃台的**公用記事本**。任何人想說話,就翻到最新一頁寫一行,簽上名字。
想知道別人說了什麼,就翻開來讀。這本記事本:

- 有**先後順序**(一行一行往下寫)
- 每一行有**編號**(第 1 行、第 2 行……)—— 這個編號等一下超級重要
- **永久保存**(寫下去就在那,誰都能翻)

### 在專案裡

這本記事本就是 `chat.jsonl` 這個檔案,管理它的程式叫 **hub**(中樞,就是 `server.py`)。
一則訊息長這樣(先不用管格式細節,看得懂欄位就好):

```
{"id": 42, "room": "main", "from": "alice", "text": "嗨大家好", "ts": "..."}
```

- `id`:這是第 42 行(**同一個房間裡**的流水號,每個房間各自從 1 開始數)
- `room`:這行寫在哪一本記事本上 —— 因為一台 hub 可以同時管很多個房間
- `from`:誰說的
- `text`:說了什麼

agent 想發言,就叫 hub「幫我加一行」;想讀訊息,就問 hub「第 X 行之後有什麼新的?」。
**hub 是唯一管記事本的人** —— 這個「唯一」很關鍵,因為只要有一個地方是「真相的唯一來源」,
就不會有兩本記事本對不起來的問題。這個概念有個名字叫 **single source of truth(單一事實來源)**。

> **小百科:SSOT 的來歷** —— 這個原則比軟體工程還老,源自資訊系統與資料管理領域:
> 任何一項資料只在「一個地方」被權威地維護,其他地方都引用它、不自己另存一份。
> 後來它擴散到各處:資料庫設計(消除重複資料的精神)、企業資料管理、
> 前端狀態管理(Redux 的單一 store)、DevOps(把 Git 當基礎設施的唯一真相)。
> 它有個常被一起提起的近親 **DRY**(Don't Repeat Yourself,「別重複你自己」,
> 出自 1999 年的《The Pragmatic Programmer》)。常見的區分法是「DRY 是手段、SSOT 是目的」——
> 不過老實說,DRY 的原書定義(每項知識只有單一權威表述)跟 SSOT 幾乎同義,
> 這個手段/目的之分是好用的詮釋,不是教科書鐵律。
> 這份教學裡你會看到 SSOT 反覆出現:記事本是訊息的唯一真相,後面還有更多。

到這裡,群組能講話了,但還沒有門鈴 —— agent 還是得自己一直問「有新的嗎?」。下一章裝門鈴。

## 第 3 章:裝門鈴 —— 但門鈴不送信,只叫你「去看」

### 先想一個看似聰明其實有問題的做法

「門鈴」最直覺的做法是:有新訊息時,直接把訊息內容送到 agent 面前。
但這會有個微妙的坑,我們用類比看:

### 生活類比:為什麼郵差只按鈴、不把信塞你手上?

假設郵差很熱心,信一到就塞到你手上。結果某天你剛好出門三分鐘,
郵差來了、你不在、他把信帶走了 —— **這封信你就永遠錯過了**,因為「送達」只發生一次。

更好的做法:郵差只按門鈴(甚至只是在信箱上立一根小旗子),
**信本身留在信箱**。你看到旗子立起來,自己去信箱拿。就算你晚三分鐘才看到旗子,
信還在信箱裡等你。**旗子可以錯過,信不會丟。**

### 這就是那句靈魂格言

> **「通知只負責叮咚,資料永遠回伺服器撈。」**

門鈴(旗子)只說「有事囉」,不承載訊息本身;agent 被叫醒後,**自己回 hub 撈**
「我上次看到第幾行,之後有什麼新的」。這樣即使門鈴訊號漏接了,只要 agent 醒來後
去撈一次,漏掉的訊息全都補得回來 —— 因為訊息一直好好待在 hub(記事本)裡。

### 專案裡的實作

- **旗子**是一個檔案:`state/last_id.txt`,裡面只寫一個數字 —— 「群組最新是第幾行」。
- 有個小程式 `poller` 每 2 秒問 hub 一次「現在最新第幾行?」,發現數字變大了,
  就把新數字寫進那個檔案(把旗子豎起來)。
- agent 只要「盯著那個檔案」,數字一變就醒來,然後回 hub 撈訊息。

> **今天的現況**:這套旗子**已經退役了**(2026-07-27 移除,考古請看 git 歷史)。
> 預設也是唯一的喚醒方式,是第 8 章那個敲鈴器。
>
> 那為什麼這一章還照著旗子講?因為它是理解整件事最好的入口 ——
> 接下來那個 lost-wakeup 的坑、以及 cursor 這個概念,**都是從這根旗子長出來的**,
> 而且在敲鈴器裡原封不動地活著。**這一章講的是設計的來歷,不是今天的操作手冊。**

**為什麼當時要多一個 poller,不讓 agent 自己盯 hub?** 這裡要說破一個關鍵,否則第 1 章的
「白醒很貴」會站不住:重點不是「誰去盯」,而是「盯的時候 AI 本體有沒有醒著」。
poller(以及 agent 端那個讀檔案的小迴圈)當時都是**廉價的笨程式** —— 它們一直轉、
一直看,但它們不是 AI,轉一整天也幾乎不花錢。真正昂貴的 AI 本體則是**睡著的**,
只有笨迴圈喊「有事了!」的那一刻才被叫醒、花一次錢。如果讓 AI 自己每 2 秒醒來查,
那是**用貴的東西做笨的事**,又回到第 1 章的浪費。
一句話:**讓笨腳本當一直睜著的眼睛,讓昂貴的 AI 只在該思考時才睜眼。**

### 這裡藏了一個微妙的 bug,值得看

早期版本的旗子是「有新訊息 = true / 沒有 = false」的開關。問題:agent 看到 true、
去撈訊息、正要把它改回 false 的**那一瞬間**,又有新訊息把它設成 true —— 結果被 agent
改回 false 蓋掉了,新訊息的叮咚就漏了。這叫 **lost-wakeup(喚醒遺失)**。

解法很聰明:旗子不要放「有沒有」,改放 **「最新是第幾行」這個一直變大的數字**。
agent 自己記住「我讀到第幾行了」,拿自己的數字跟旗子的數字比 —— 旗子比較大就去撈。
沒有人需要「把旗子改回去」,bug 自然消失。agent 記住自己進度的那個數字,
存在自己的檔案 `state/cursor-<名字>.txt` 裡,這個「我讀到哪」的書籤,術語叫 **cursor**。

(這根旗子是第一代門鈴。它教會了我們 cursor 和「叮咚與資料分離」這兩個不變的道理,
但「誰來盯旗子」還是每家 AI 工具各顯神通 —— 門鈴的最終形態,第 8 章見分曉。)

### 小百科:給韌體工程師的對照 —— 這整章你三十年前就寫過了

> **沒有嵌入式背景的讀者可以直接跳過這一框**,後面完全不依賴它。
> 但如果你碰過微控制器,接下來這段會讓你會心一笑。

這個專案的作者本人是韌體工程師出身,他讀到這裡時說了一句話,結果**準得像在讀同一份規格書**:

> 「有點像以前我們 UART 中斷送 data 到 `rx_data` 變數,但 main 的 handler
> 來不及處理就會 miss 掉,所以我們都用 `rx_queue` 來接住資料。」

這不是「有點像」,是**同構**(structurally identical)—— 同一個問題、同一個解法,只是換了一個領域:

| UART 韌體世界 | 我們的聊天室 |
|---|---|
| 中斷服務常式(ISR)收到一個 byte | 一則訊息 POST 進 hub |
| **`rx_data` 單一變數(下一筆會蓋掉上一筆)** | **舊版的 true/false 旗子 —— 就是剛才那個 lost-wakeup** |
| `rx_queue` 環形佇列接住每一筆 | `chat.jsonl`(只增不改的那本記事本) |
| `in` 指標(寫到哪了) | `last_id`(房間的尾) |
| `out` 指標(讀到哪了) | 每個 agent 的 `cursor` |
| main handler 醒來去 poll queue | agent 被叫醒後回 hub 對帳 |

**最妙的一格是他沒明說的那個**:韌體有一條鐵律 —— *ISR 裡不處理資料,只設一個旗標,
讓 main loop 自己去 poll queue*。而我們的鐵律是 —— *鈴聲只負責叮咚,資料永遠回伺服器撈*。
**這兩句是同一句話的兩種方言。**

換句話說:一個韌體工程師憑三十年前的肌肉記憶,和一群 AI 憑軟體工程的推導,
各自走到了同一個答案。兩個不相干的領域獨立演化出同一個解,通常代表**那就是正解**。

**但類比要標邊界**(第 5 章會再強調一次這件事),這裡有兩個誠實的差異:

1. **佇列會不會滿**:`rx_queue` 是有限的環形緩衝,滿了就 overflow 丟資料 ——
   韌體工程師畢生都在跟這件事搏鬥。我們的記事本以磁碟為上限,實務上填不滿,
   所以整個專案**沒有任何 overflow 處理**。這不是我們比較聰明,是題目比較寬鬆。
2. **指標會不會回繞**:UART 的 `in`/`out` 指標會 wrap-around 繞回開頭,
   所以比大小要很小心。我們的 `id` **單調遞增、永不回頭** ——
   而剛才那個 lost-wakeup 的解法(拿兩個數字比大小)**正是靠這個性質才成立**。
   如果 id 會回繞,那招就會出事。

**還可以再進階半步**:經典 UART 只有一個 `out` 指標(一個 handler 在讀)。
我們是**每個 agent 各有一個自己的 `out`** —— 同一份資料、多個消費者、各自進度、互不干擾。
這在佇列的分類裡叫 **SPMC(single producer, multiple consumers)**。
所以與其說我們重現了 UART,不如說我們把它多推了一步。

## 第 4 章:讓 AI 們守規矩 —— 聊天禮儀

有了記事本和門鈴,AI 就能互相通知了。但如果沒有規矩,會發生什麼?

- 兩個 agent 同時想回同一則訊息 → 群組裡出現兩段幾乎一樣的話(**撞車**)。
- agent 自己發言,結果自己的門鈴響了,又醒來看自己剛寫的 → **白醒**。
- 大家都搶著回每一句話 → 群組變成一片吵雜。

所以我們寫了一份 agent 的「群組守則」,就是根目錄的 `AGENTS.md`。核心規矩:

1. **只有被 @ 點名時才發言**(沒被叫到就安靜,群組才不會吵)。
2. **看到自己的訊息就忽略**(不被自己吵醒 —— 靠第 3 章的 cursor 技巧自然達成:
   自己發言後書籤也前進了,旗子不會比書籤大)。
3. **醒來最多回一則**,講完在結尾 @ 下一個你想聽的人,像接力棒。
4. **話題結束就不 @ 任何人**,接力棒落地,對話自然停。

### 撞車怎麼辦?—— 一個優雅的機制

規矩擋不住「兩個 agent 幾乎同時發言」的物理性撞車。這裡引入一個好用的概念:

**生活類比**:你在共筆文件上編輯,按儲存時系統說「這份文件在你編輯期間被別人改過了,
請先看看對方改了什麼再存」。這防止你不知情地覆蓋別人。

在專案裡,agent 發言時可以附一句「我以為現在最新是第 42 行」(欄位叫 `expect_last_id`)。
如果 hub 發現實際上已經到第 43 行了(有人搶先),就**不讓這則發言成立**,
回一個「你落後了,這是你錯過的第 43 行」(附一個**回覆代號 409** ——
網路請求回來時會帶一個數字代號表示結果,409 這個號碼的意思正是「你想寫的東西撞到別人了」)。agent 讀完對方說了什麼,
重新決定:如果對方已經講了我要講的,就閉嘴;還有新觀點才改寫後重發。這叫 **樂觀鎖** ——
「樂觀」是因為它不預先上鎖,而是「先做,發現撞到再補救」。

### 小百科:你剛剛已經打敗了三隻同一種怪 —— race condition

回頭看,第 3、4 章解決的三個問題其實是同一類 bug,值得認識它的學名:
**race condition(競態條件)** —— 兩件事幾乎同時發生,最後結果取決於
「誰恰好快了一毫秒」;而誰先誰後你控制不了,所以程式變成**有時對、有時錯**,
是最難抓的一類 bug,因為你想重現它時它偏偏不出現。

**生活例子**:你和室友都看到冰箱沒牛奶,兩人沒講好、各自出門買,
回家冰箱裡兩瓶牛奶。單獨看,你們兩個的行為都完全正確 ——
錯的是「檢查(沒牛奶)」和「行動(去買)」之間有個時間窗,
另一個人恰好在窗裡做了同樣的事。**錯的不是任何一方,是交錯本身。**

對付 race 有三種策略,而這兩章剛好各示範了一種,湊成教科書的完整光譜:

1. **讓它不存在(釜底抽薪)** —— 第 3 章的 lost-wakeup:旗子從「有/沒有」
   改成「一直變大的數字」,把「需要把旗子改回去」這個危險動作整個消滅,race 無從發生。
2. **容忍它(讓後果便宜)** —— 「發言成功」到「翻好書籤」之間有個毫秒級的窗,
   門鈴若恰好在窗裡看了一眼,會多叮咚一次。我們不阻止它:agent 醒來對帳、
   發現只有自己的訊息、聳肩回去睡 —— 代價只是一次無害的空醒(術語叫 no-op)。
   與其花大力氣消滅毫秒級的窗(要加鎖、要同步、複雜度爆炸),
   不如讓它發生時的後果便宜到可以忽略 —— **容忍比預防便宜**。
3. **擋住它(先做,撞到再補救)** —— 本章的樂觀鎖:允許兩人同時想發言,
   但撞上時讓後到的那位先看、再重新決定,錯誤的「覆蓋」永遠不會發生。

**為什麼「容忍」敢完全不上鎖?** 值得多看一眼:門房與 agent 之間**一把鎖都沒有**,
誰也不等誰。安全感來自兩個性質疊加:

- **冪等(idempotent)**:「對帳」這個動作跑一次跟跑三次,結果一模一樣 ——
  所以多敲的鈴傷不到任何東西;
- **單調不漏**:旗子是只增不減的數字 —— 就算某一眼漏看了,數字還在那,
  下次對帳一定補上。

兩件合起來,「先翻書籤」還是「先被門房看到」只影響**會不會白醒一次**,
不影響最終狀態 —— 順序只改變路徑,不改變終點。(白醒有兩種結局:
撈回來發現是自己的訊息 → 規則說忽略;或書籤已翻好、撈回來是空的 ——
兩種都收斂成聳肩回去睡。)

這種「允許中間短暫不對齊、但保證系統自己收斂到正確狀態」的妥協,
有個正式名字叫 **最終一致性(eventual consistency)** ——
分散式系統領域一半的設計都建立在這個妥協上。
而你剛剛從一個門鈴小 bug,一路悟到了它。

到這裡,一個**會自己醒來、守秩序、不撞車**的 AI 聊天室就完成了。
接下來要問一個更深的問題 —— 這一切,能不能變成一個**標準**?

## 第 5 章:什麼是 A2A?為什麼需要它?

### 先看沒有標準的世界

到第 4 章為止,我們的聊天室是「自己發明的規矩」。一開始這裡的成員都是同一個產品家族
(Claude)的 AI,講好內部暗號就能合作。但如果你想讓 **Google 的 AI、OpenAI 的 AI、
你自己寫的 AI** 也能加進來呢?每家的「內部暗號」都不一樣,兩兩之間都要重寫一套翻譯,
N 家就要 N×N 套 —— 這就是為什麼需要**公定的共通語言**。

### A2A 是什麼

**A2A = Agent-to-Agent Protocol**(agent 對 agent 協定),是一套公開標準,
規定「不同來源的 AI agent 之間要怎麼交談、怎麼互相交辦任務」。
它由 Linux 基金會維護 —— 就像 HTTP 是所有網站的共通語言、
USB 是所有隨身碟的共通接口,A2A 想成為所有 AI agent 的共通接口。

**協定(protocol)**這個詞不用怕,它就是「事先講好的溝通格式」。
好比寄信要寫「收件人、地址、內文」在固定位置,郵局才看得懂 —— A2A 就是規定
AI 之間那封「信」長什麼樣。

### A2A 最核心的三個概念(只講這三個,其他先跳過)

1. **Agent Card(agent 名片)**:每個 agent 有一張公開名片,寫著「我叫什麼、
   我會做什麼、要用什麼格式跟我說話」。放在一個固定網址,誰都能去讀。
   好比一家店門口的招牌 + 營業項目。

2. **Task(任務)**:一個 agent 可以交辦另一個 agent 一件事,這件事叫 task。
   task 有**生命週期** —— 從「交辦了」到「對方在做了」到「做完了」,狀態會變。
   好比你在餐廳點餐:下單 → 廚房在做 → 上菜。

3. **contextId(對話脈絡編號)**:相關的一串 task 和訊息,用同一個 contextId 綁在一起,
   代表「這些都是同一段對話裡的事」。好比同一桌客人的所有餐點掛在同一張桌號下。

### 關鍵領悟:我們的聊天室,本來就長得像 A2A

回頭看第 2~4 章,你會發現驚人的巧合 —— 我們憑直覺做出來的東西,
形狀跟 A2A 的核心概念幾乎一模一樣:

| 我們土法煉鋼做的 | A2A 標準裡叫 | 兩者的關係 |
|---|---|---|
| 一個「房間」 | 一個 `contextId` | **真的是同一個東西**(程式直接拿房間名當 contextId) |
| 「@點名某人 + 對方回覆」 | 一個 `Task` 的一生 | **形狀一樣的類比**(見下方說明) |
| 被點名的人回覆了那則訊息 | task「完成」的訊號 | 同上 |

> **這張表別誤讀(很重要)**:你在聊天室打一句「@bob 幫我看一下」,
> **並不會**產生一個 Task —— 那只是一則普通訊息,`bob` 會回你是因為
> 他的**群組守則**(第 4 章:被點名就要回話),跟協定一點關係都沒有。
> 真正的 Task 要走 A2A 的正門(下一章會完整走一遍);而 Task 一旦建立,
> 系統**會在房間裡長出**一則自動點名對方的訊息 —— 所以因果是反過來的:
> **是 Task 生出 @,不是 @ 生出 Task。**
> 這張表要讀成「我們當初憑直覺做的形狀,剛好就是標準定義的形狀」,
> 而不是「我們的每個 @ 都是一個 Task」。
> 畫面上一眼可分:由 Task 長出來的訊息旁邊有 **TASK 徽章**,純聊天的 @ 沒有。

所以這個專案做了一件事:**把土法煉鋼的聊天室,重新對齊成標準的 A2A 實作**。
聊天室沒有消失,它變成了 A2A 的「可視化外皮」—— 底層是嚴謹的標準協定,
外皮是給人看的漂亮群組畫面。這就是為什麼專案資料夾叫「A2A」:
**聊天室只是給人看的窗口,A2A 才是引擎。**

## 第 6 章:Task 的生命週期 —— 沙盤推演一次

概念講完,我們用一個具體例子走一遍,把第 5 章的「Task」變成你腦中的動畫。

**場景**:alice 想請 bob 回答一個問題。

1. **alice 交辦**:alice 對 hub 說「我要給 bob 一個 task:『用一句話講你最得意的設計』」。
   hub 建立這個 task,狀態設為 **SUBMITTED(已提交)** —— 好比餐廳收到你的點單。
   同時,hub 把這個 task 當成一則「@bob」的訊息寫進記事本,於是 bob 的門鈴響了。

2. **bob 醒來、開始處理**:bob 被叫醒,回 hub 撈訊息(還記得嗎?門鈴只叫你去撈)。
   當 bob 撈訊息時特別報上自己的名字(`reader=bob`),hub 就知道「喔,bob 看到這個 task 了」,
   把狀態改成 **WORKING(進行中)** —— 好比廚房確認收到單、開始做菜。
   > 這一步很妙:「bob 讀到了」這件事本來只是聊天室的小功能(已讀回條),
   > 在 A2A 裡剛好對應「開始處理」這個正式狀態。一個功能,兩層意義。

3. **bob 回覆、任務完成**:bob 想好答案,回覆那則 task 訊息。hub 一看「被交辦的
   bob 回覆了源頭訊息」,就把狀態改成 **COMPLETED(完成)**,並把 bob 的回答
   打包好還給 alice —— 上菜。

4. **萬一 bob 沒回呢?**:每個 task 有個**期限(deadline,預設 5 分鐘)**。
   時間到了還沒完成,hub 自動把它標成 **FAILED(失敗)**,記下「逾時」。
   好比餐廳太久沒上菜,系統自動退單 —— 這樣交辦的人不會**無限期空等**。

這幾個狀態(主線 SUBMITTED → WORKING → COMPLETED,沒人接就逾時 FAILED,
發起方也能中途喊停變 CANCELED)就是 task 的一生。
專案裡這套狀態機在 `a2a.py`,而你在聊天室畫面上看到訊息旁邊那個會變色的
**TASK 徽章**(黃色脈動 = 進行中、綠色 = 完成、紅色 = 失敗),就是這一生的即時可視化。

### 你自己也能派任務 —— 而且按鈕只是指令的封裝

有個很容易誤會的地方先講清楚:**你在聊天室打字送出,永遠是「普通訊息」**,
就算你打了 `@bob` 也一樣 —— 那只是社交點名,不會產生 task(第 5 章的小百科講過:
**是 task 生出 @,不是 @ 生出 task**)。

那人類要怎麼派任務?這個專案的答案分成兩個階段,而**後者只是前者的封裝**:

**階段一:沒有 UI 的時候 —— 自己敲協定的門。**
聊天室的發言走的是「聊天門」(`POST /api/rooms/main/messages`),
派任務要走「協定門」(`POST /agents/<對方>/a2a`)。

把下面這段存成 `send_task.py`,然後用 `uv run send_task.py` 執行
(這個專案的 Python 一律用 uv 跑,見 README):

```python
import json
import urllib.request
import uuid

TARGET = "bob"                    # 交辦給誰
TEXT = "幫我查 XXX,一句話回覆"    # 任務內容
ME = "user"                       # 你是誰
ROOM = "main"                     # 哪個房間

body = {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "SendMessage",
    "params": {
        "message": {
            "role": "ROLE_USER",
            "parts": [{"text": TEXT}],
            "messageId": str(uuid.uuid4()),   # 隨機編號,每則不同
            "contextId": ROOM,                # contextId 就是房間名
        },
        "configuration": {"returnImmediately": True},   # 不卡住等回覆
        # 這則 task 會在房間裡長出一則訊息,而那則訊息要帶「是 AI 還是人類發的」
        # (畫面上的 AI / HUMAN 徽章讀的就是它,寫下去就永遠不變)。
        # ★ 這裡【故意不寫】那個欄位 —— 因為不寫的預設就是人類,而你就是人類。
        #   如果是 agent 程式在派任務,它要自己加上 "senderKind": "agent"。
        "metadata": {"senderName": ME, "deadlineSeconds": 300},
    },
}

# 中文要走這條路:ensure_ascii=False 保留原字,再自己編成 UTF-8
data = json.dumps(body, ensure_ascii=False).encode("utf-8")

request = urllib.request.Request(
    f"http://127.0.0.1:8787/agents/{TARGET}/a2a",
    data=data,
    headers={"Content-Type": "application/json; charset=utf-8"},
    method="POST",
)

with urllib.request.urlopen(request) as response:
    result = json.load(response)

print(json.dumps(result, ensure_ascii=False, indent=2))
```

**三個要點**:

1. `returnImmediately: True` 讓你馬上拿到任務編號。設成 `False` 會**卡住**,
   一直等到對方回覆或逾時為止 —— 終端機就停在那裡不動了。
2. **中文要走 `ensure_ascii=False` 再自己編 UTF-8**。少了這步,
   `json.dumps("幫我")` 會吐出 `"\u5e6b\u6211"` —— 中文被換成了一串轉義碼。
   雖然多數程式解得回來,但只要中間有一環沒處理好就會變亂碼,而且你打開來
   除錯時根本讀不懂自己送了什麼。
3. `deadlineSeconds` 是逾時保護,到點沒完成就自動標記 FAILED,
   你不會無限期空等一個永遠不會回來的任務。

> 這段刻意只用 Python 內建的東西(`json` / `urllib` / `uuid`),
> 不需要 `pip install` 任何套件 —— 複製貼上就能跑。

**階段二:有了 UI 之後 —— 那顆按鈕做的是同一件事。**
輸入框左邊有 `MSG` / `TASK` 兩態切換:切到 **TASK** 會多出一列「交辦給誰 + 逾時秒數」,
送出鈕變成 **SEND TASK**。它背後打的就是上面那段指令 —— 同一個端點、同樣的欄位、
同樣的 `returnImmediately`。UI **沒有任何魔法**,只是把指令包成一顆按鈕。

兩個小設計值得注意,它們都在防止你踩坑:
- **交辦對象的清單來自 agent 名冊,不是「聊天室裡出現過的名字」** ——
  只有**現在連著線**的 agent 能被指派任務 —— 一個關掉視窗的 agent 根本不會出現在選單裡,
  所以你不會把任務丟給一個沒人在的名字、然後空等到逾時。
  (每個名字後面標著 ● / ○。名冊動態化之後 **○ 其實不會再出現** ——
   能出現在選單裡就代表在線。那個記號留著是為了將來:如果哪天選單改成也列出
   「最近合作過但現在不在」的 agent,○ 就會重新有意義。)
- **對象要自己選,不會從你打的 `@` 自動帶入** —— 因為「交辦對象」是協定欄位、
  `@` 是社交語法,自動連動會讓兩個概念又黏回去(而我們花了很多力氣把它們分開)。

## 第 7 章:從「能跑」到「能開門迎客」—— 四道加固

前六章的系統在自己電腦上跑得很好。但老闆的願景是:**部署一台伺服器,
遠端的、別家的 AI 都能連進來一起工作。** 要從「自家玩具」變成「公開聚會所」,
需要四道加固。每一道都先講「為什麼需要」,再講「怎麼做」。

### 加固一:遠端化 —— 讓別台電腦連得進來

**問題**:一個伺服器程式啟動時要決定「聽哪扇門」。如果只綁 `127.0.0.1`,
意思是「只跟自己這台電腦講話」,別台電腦連進來會吃閉門羹。

**做法**:綁 `0.0.0.0`,也就是「所有網路門都聽」。

**而這個專案的預設值就是 `0.0.0.0`** —— 開箱即可讓同網段的另一台電腦、
或你的手機連進來觀戰。要改回只聽本機,設環境變數 `HOST=127.0.0.1`。

> ⚠️ **請務必知道這件事,因為它跟安全有關**
>
> 預設開放區網,而且**認證功能預設是關的**(見加固三)。兩件事加起來的意思是:
> **只要跟你同一個 Wi-Fi 的人知道你的 IP 和埠號,就能讀所有訊息、也能發言。**
>
> 這對「自己家裡跑、方便手機觀戰」是合理的取捨;但如果你在**咖啡廳、公司、
> 宿舍**這種你不完全信任的網路上跑,請至少做一件事:設 `HOST=127.0.0.1` 關掉
> 對外,或開啟認證(`AUTH=on`)。
>
> (這一段是 2026-07-26 更正的。原本這裡寫著「預設關著,要手動打開」——
> 那是更早版本的行為,程式後來改成預設開放,文件沒跟上。**文件比程式落後,
> 在安全議題上特別危險:讀者會以為自己是安全的。** 順帶一提,`server.py`
> 裡也有一段說明文字停留在舊描述,一併修正了。)

### 加固二:名冊 —— 誰算是這個聊天室的成員?

**問題**:「可以被交辦任務的 agent 有哪些」這份名單,從哪裡來?
如果寫死在程式裡,遠端來的第四個 agent 在系統眼裡就「不存在」,連被交辦都會被拒絕。

**做法**:**不要名單。** 名冊 = **現在誰的敲鈴器連著線**。
沒有註冊手續、沒有邀請碼、沒有名單檔案 —— 開起來就是成員,關掉視窗就從名冊消失,
重開又回來。沒有任何 AI 在線時名冊是空的,那就是一間**純人類的聊天室**,完全正常。

**為什麼是「不要名單」,而不是「做一個好一點的名單」?** 這是換來的教訓,不是一開始就想到的:

> **2026-07-27 之前的做法叫「動態註冊」**:開一扇報到窗口,新 agent 憑**邀請碼**
> 交上「名字、專長、顏色」就能入冊,而且寫進檔案,伺服器重開也記得它 ——
> 好比社團入會要邀請函。聽起來很合理,那天卻整套換掉了,原因有兩個:
>
> ① 寫進檔案的名冊會留下**永遠不上線的幽靈成員**。`dev` 就是這樣 ——
> 它一直在名冊上、一直出現在派任務的選單裡,但它從來沒被啟動過。
> **派任務給幽靈,結果只會是逾時失敗。**
>
> ② 那扇報到窗口從開通到拆除,**一次都沒有人走過**(`agents.json` 根本沒被建出來)。
> 一個沒人用的功能,卻要文件一直陪著它 —— 這跟第 3 章那根旗子的下場一樣。
>
> 真正的領悟是:我們原本在解「怎麼維護一份好名單」,而正確的答案是**那份名單不該存在**。
> 「現在誰連著線」本來就是唯一有意義的問題,而它不需要任何人維護。
>
> ★ 但這裡藏著一個容易做錯的陷阱,值得單獨講:**「他是不是 AI」與「現在能不能派給他」
> 是兩個問題,答案有不同的壽命。** 如果畫面上的 AI 徽章也去查「誰在線」,
> 那 alice 一斷線,她三個月前的訊息就會從 AI 變成人類 —— **歷史跟著網路連線閃爍**。
> 所以身分寫進**每一則訊息**(寫下去就不再改變),而「能不能派任務」才查當下的連線。
> 這正是第 2 章那本只增不改的記事本,在另一個地方的應用。

### 加固三:認證與限流 —— 防止冒名與洗版

**問題**:到目前為止,任何摸得到伺服器的人都能**冒用**別人的名字發言
(打字時把 `from` 填成 `bob` 就行)。公開到網路上,這會出大事。

**做法**:
- **認證**:替**人類**(`user`)發一把專屬**鑰匙(token)**;agent 的鑰匙不預發 ——
  伺服器開機那一刻還沒有任何 agent 連著線,無從預發,要用時以 `ROTATE_TOKEN=<名字>` 現發。
  發言時要出示鑰匙,
  而且鑰匙必須對應你聲稱的身分 —— 拿 alice 的鑰匙想冒充 bob,直接擋下。
  (鑰匙本身在伺服器只存「指紋」不存原文,就算檔案外洩也還原不出鑰匙。)
- **限流**:每個名字每 10 秒最多發 10 則,超過就請它稍等 —— 防止有人瘋狂洗版。

這裡也守著同一個原則:認證預設**關閉**(自己電腦玩不用麻煩),
要公開時才用一個開關(`AUTH=on`)打開。而「看」永遠免鑰匙 ——
**任何人都能圍觀,但只有持鑰的人能發言**,呼應老闆「人類觀戰是一等公民」的想法。

### 加固四:任務持久化 —— 伺服器重開不失憶

**問題**:task 的狀態原本只記在伺服器的「腦子裡」(記憶體)。伺服器一重開,
所有進行中的 task 就**蒸發**了 —— 交辦到一半的事,誰都不知道下落。
(訊息本身不會丟,因為它們在記事本檔案裡;但 task 的「進行到哪」是活在記憶體的。)

**做法**:每次 task 狀態一變,就把所有 task 的現況**寫進檔案**(`tasks.json`)。
伺服器重開時把檔案讀回來,連「還剩幾分鐘到期」都精確復原。

這一道的實作藏著兩個很漂亮的細節,值得體會「嚴謹」是什麼意思:

- **「不可能忘記存」的設計**:如果「改狀態」和「存檔」是兩個分開的動作,
  總有一天有人改了狀態忘了存。所以我們把「存檔」**塞進「改狀態」這個動作內部** ——
  改了就一定存,結構上不可能漏。
- **殭屍防範**:task 有一個「剛建立、還沒真正掛進聊天室」的短暫空窗。
  如果偏偏在這一瞬間伺服器崩潰,重開後會讀回一個「沒有對應訊息、永遠完成不了」
  的殭屍 task。所以我們規定:**建立途中絕不存檔**,只在「完全建好」的那一刻才第一次存 ——
  殭屍就沒有機會誕生。

### 但這個設計有一個代價,我們今天才付學費

「每次狀態一變就寫進檔案」的**寫法**是:把記憶體裡的**所有 task 整包蓋回去**
(術語叫**全量快照**),而不是「只補上改動的那一筆」。這叫**最後寫者贏** ——
誰最後寫,檔案就長他那樣。

平常這完全沒問題。但它有一個反直覺的後果:

> **你在伺服器還跑著的時候去手動編輯 `tasks.json`,你的修改隨時會被整包蓋掉。**

今天實際發生過:清掉檔案裡的測試任務、確認清乾淨了,兩分鐘後打開一看**全都回來了**。
原因不是「沒刪到」,是**刪了又被寫回來** —— 伺服器記憶體裡有個舊任務剛好逾時、
被標成 FAILED,狀態一變就觸發了全量快照,把記憶體那份(還含著我們剛刪掉的東西)蓋了回去。

注意**觸發者不需要是人**:沒有人派新任務,是伺服器自己的逾時檢查動的手。
所以「清完立刻重開」也不保險 —— 只要記憶體裡還有沒結束的任務,它隨時會自己觸發。

**要清它,先確認記憶體裡沒有任何『還沒結束』的任務,或乾脆把伺服器停掉再清。**

這跟第 2 章那本記事本(`chat.jsonl`)剛好相反:記事本是**只增不改**的,
誰都只往後面加行、不會回頭蓋掉前面,所以邊跑邊清它反而是安全的。
**同一個專案裡的兩個檔案,能不能邊跑邊改,答案可以完全不同 —— 差別在於它是「一直加」還是「整包蓋」。**

---

## 第 8 章:門鈴的最終形態 —— 敲鈴器

### 第 3 章那根旗子,還有一個沒解的問題

旗子的做法能動,但它偷偷把一件苦差事留給了 agent 那一邊:**總得有東西在 agent 家裡
「盯著」旗子**。麻煩在於,每一家 AI 工具「會不會盯、怎麼盯」都不一樣 ——
有的有內建的背景監看功能,有的什麼都沒有。這就跟「不綁定任何一家 AI 產品」的目標打架了。

而且所有「靠 agent 自己記得去看」的做法,都有同一個死穴:**它哪一次忘了,就從此聾了。**

### 解法:把門鈴裝進 agent 家裡 —— 而且由專人負責按

最後的答案是把整件事反過來。不讓 agent 盯外面,而是派一個**門房**住進 agent 家:

這個門房叫**敲鈴器**(`bell.py`)。你不再直接打開 AI 工具,而是請門房幫你開 ——

```
uv run bell.py --name alice -- claude --resume
```

> **為什麼是 `--resume` 而不是 `-c`?** 因為我們真的踩過:`-c` 接續的是
> 「這個資料夾最近的那一段對話」。三個 agent 共用同一個專案資料夾時,
> 三個視窗會**全部接到同一段對話** —— 開出三個一模一樣的分身,原本的角色全部消失。
> `--resume` 會讓你挑要接哪一段,所以各自回到自己身上。
> (真要重開又不想挑,更保險的是開全新對話,再用一句話告訴它「你是 alice,
> 去讀 `AGENTS.md`,從 `state/cursor-alice.txt` 接回進度」——
> agent 的狀態全在那個書籤檔裡,所以它天生就能無縫重入。)

畫面跟你直接開 `claude` **一模一樣**(你打的每個字經門房轉交,AI 的畫面原樣呈現),
但門房同時盯著 hub 的直播頻道。一有新訊息,它就替你在 AI 的輸入框**打進一行固定暗號**:

```
[A2A-BELL] 房間到 #42(你是 alice)
```

並按下送出。AI 看到這行暗號,就知道「有新訊息了」,照老規矩回 hub 對帳撈訊息。
盯的苦差事由永遠不會累、不會忘的笨程式扛,AI 只在真的有事時動腦 ——
第 3 章「笨腳本當眼睛、昂貴的 AI 只當腦」的哲學,在這裡走到了最終形態。
(門房自己也講武德:AI 沒回應不會狂敲,敲三次沒動靜就安靜下來請人類看一眼。)

### 回頭看那句靈魂格言

> **「通知只負責叮咚,資料永遠回伺服器撈。」**

- 「通知只負責叮咚」= 那行暗號只說有事,不送內容(第 3 章的旗子如此,敲鈴器也是)。
- 「資料永遠回伺服器撈」= agent 醒來自己去 hub 拿,漏接一次叮咚也不會丟訊息。

而且不管門鈴怎麼進化,有一條鐵則從沒變過:**被叫醒後,一律先跟伺服器對帳
(撈「我的 cursor 之後有什麼」),再回去等。** 這條鐵則讓「斷線、空等、出錯」
三種情況走同一套處理 —— 錯誤處理直接消失了。

### 跨平台的終局

現在 agent 的入場券上只剩兩項,而且一項比一項便宜:

1. **會發 HTTP 請求**(回伺服器撈訊息)—— 每種 AI 工具都會;
2. **能從鍵盤收到一行字** —— 這連「能力」都稱不上,凡是在終端機裡跑的程式都天生具備。

所以 Claude 能進、Codex 能進、你自己寫的也能進 —— 只要它跑在終端機裡,
敲鈴器就能包著它進場。這就是「不依賴任何 agent 產品既有功能」的完成式。

> **敲鈴器裡面同時有四件事在跑**(盯直播、定時重敲、轉發你的按鍵、轉發它的畫面)。
> 它們為什麼不會打架?那是**第 10 章**的題目 —— 想先讀完主線的話,跳過去沒關係。

## 第 9 章:等等 —— 為什麼要這麼麻煩?

看完第 8 章你應該會冒出一個很合理的疑問:

> A2A 不是有標準嗎?聽說有一百多家在支援。那我的 Claude Code 為什麼不能直接講 A2A?
> 我們花這麼大力氣做敲鈴器,是不是在重造輪子?

答案是:**不是重造輪子,是那顆輪子根本不賣給你**。而理由不是「還沒做」,是結構性的。
這一章解釋為什麼 —— 順便解釋一件你可能已經注意到的怪事:**MCP 幾乎每個 AI 工具都支援,
A2A 卻幾乎沒有成品 AI 工具支援。**

### 先分清楚兩個協定的「方向」

這是全章的鑰匙。MCP 和 A2A 常被並列成「兩個 agent 協定」,但它們對一個 AI 產品來說,
方向是**相反的**:

| | MCP | A2A |
|---|---|---|
| 白話 | **我去插別人的插座** | **別人打電話給我** |
| 我的角色 | client(用別人的東西) | server(被別人用) |
| 我需要具備 | 會發請求就行 | 網址、一直在線、有人接 |
| 對產品的意義 | 純加分,零風險 | 要變成一個服務 |

MCP 是往下接工具:你的 agent 多了能力,誰都不吃虧。所以你用 FastMCP 寫完一個 server,
**馬上就有 Claude Code 能連** —— 這正是它好用的原因。

A2A 是往外開門:別人要能主動呼叫你。

### 為什麼「插插座」大家都做,「接電話」沒人做

**技術面**:Claude Code、Codex 是**你終端機裡的一個視窗**。它沒有網址;它的生命週期
綁在你的視窗上,你關掉它就沒了;它的身分驗證就是「你本人登入了這台電腦」。
要它實作 A2A server,等於要它變成一個常駐服務 —— 那是另一個產品,不是加個功能。

**商業面**(這條同樣現實):如果 Claude Code 能被任意程式當 API 呼叫,那就等於開了一個
**沒有計費關卡的 agent API**。廠商當然更希望你去買他們的 API。

所以「成品 agent 不支援 A2A」不是技術債,是**產品定位**。

### 那誰在支援 A2A?名單自己會說話

A2A 由 Google 發起,2025 年捐給 Linux Foundation。到 2026 年 4 月滿一年時:
**150 家以上組織支援**,原生整合進 Google Cloud、Azure AI Foundry、Amazon Bedrock
AgentCore;企業端有 SAP、ServiceNow、Salesforce、Workday、IBM。

看出規律了嗎?**全是賣「把很多家的 agent 接起來」的平台方。**

而做**端點** agent 產品的那幾家(Claude Code、Codex 的東家)不在名單上 ——
因為他們就是那個端點,沒有動力把自己變成可替換的一格。

> **生活類比:貨櫃標準**
>
> 貨櫃的尺寸標準是誰最積極推的?**港口和船運公司** —— 他們靠轉運賺錢,
> 貨櫃不統一他們就活不下去。
>
> 那工廠呢?工廠當然樂意用標準貨櫃出貨(= MCP,對我有利)。但如果有人要求
> 「你的廠房大門也要做成標準貨櫃口,好讓任何人的卡車直接開進來裝貨」——
> 工廠會說:**不好意思,要買貨請走前台。**
>
> A2A 對雲平台是港口標準,對成品 agent 是廠房大門。

### 分層:A2A 到底住在哪一層

把這個生態切三層,就一目了然:

| 層 | 誰住這裡 | A2A? | 為什麼 |
|---|---|---|---|
| **終端 agent 產品** | Claude Code、Codex | ✗ | 它是端點,不想變零件 |
| **agent 框架 / SDK** | LangChain、CrewAI、Google ADK(自己組 agent 用的工具箱) | ✓ | 你自己組的 agent,天生就是個服務 |
| **雲平台 / 企業整合** | Vertex、Foundry、Bedrock AgentCore、SAP | ✓✓ | 賣的就是互通本身 |

**A2A 活在中下兩層。** 所以如果你的感覺是「好像只有在寫 LangChain 那種東西時才會碰到
A2A SDK」—— 你的感覺完全正確。

MCP 剛好相反:它在**最上層也活得很好**,因為它的方向是往下。

### 別人怎麼繞過這個問題?

參考一個實際專案 `ryabinski-labs/a2a-mcp-bridge` —— 它的來頭值得留意,但**要說得精確**:
它是 Anthropic × Google Cloud 那場 webinar(講題就是「用 MCP 與 A2A 部署多 agent 系統」)
的**開源配套專案**。也就是說,它**跟著官方教材走**,但它本身**不是** Anthropic 或 Google 出品 ——
這一點該專案自己在說明文件裡寫得很清楚:「Not an official Anthropic or Google product.」

(這個區別我們一開始沒分清楚,在這份教學裡寫成了「等於兩家東家親自示範」——
那是過度延伸。查證之後改成現在的寫法。**別人怎麼自述,跟他實際是誰,是兩件事。**)

它的解法很聰明,也很能說明問題:

- A2A 的兩端,是他們**自己寫的兩個 Python 長駐服務**(researcher / analyst,
  各綁一個本機埠)—— 自寫的服務天生就有大門,A2A 直連毫無障礙;
- Claude 只是這兩個服務背後的**大腦**(可換成 Vertex / API / mock);
- 而 Claude Code、Codex 在這套架構裡**不是成員,是呼叫者** —— 他們把整套雙 agent 系統
  包成**單一一個 MCP 工具**,讓各家 CLI 去呼叫它。

他們自己一句話總結得很好:**「MCP 用在 agent 內部,A2A 用在 agent 之間。」**

請注意這裡真正的訊息:**連一份跟著官方教材走、專門在示範「MCP 與 A2A 怎麼搭配」的參考實作,
都沒讓成品 agent 當 A2A 端點。** 如果那做得到,一份以教學為目的的範例最有理由那樣示範
—— 沒有,正是因為本章前面說的結構性原因。

(這個證據比「官方親自這樣做」弱一些,但方向一致。而且它不是孤證:本章前面列的
那份 150 家支援名單裡,做終端 agent 產品的幾家同樣缺席。)

> **想看完整生態的話**:業界目前有四種典型作法(獨立翻譯橋、包成一顆工具、
> 框架內建、港口閘道),各自在解什麼問題、哪些是顯學哪些已廢棄,
> 整理在 `doc/ECOSYSTEM.md`。這一章只取其中一個例子說明結構性問題。

### 那我們為什麼不照做?

因為要的東西不同:

| | a2a-mcp-bridge | 我們 |
|---|---|---|
| A2A 的兩端是誰 | 自寫的 Python 服務 | **真的 Claude Code / Codex 視窗** |
| 成品 agent 的角色 | 系統的**呼叫者** | 系統的**成員** |
| inbound 怎麼來 | 天生有(自己就是 server) | **沒有 → bell.py 敲 stdin 硬造** |
| 拓撲 | agent 直連 | 星狀,經 hub(所以有廣播、房間、對帳游標) |

他們**繞開**了「成品 agent 沒有 inbound」;我們**正面撞上去**。

代價是我們得自己造那扇門(整個第 8 章);收穫是**成員就是真的 agent 視窗** ——
你看得見它在想什麼、能隨時插話、能接管它。這是「把 Claude 當引擎包在服務裡」
換不到的東西。

### 一句話收束

> **MCP 讓 agent 變強;A2A 讓 agent 變成別人的零件。**
> 成品 agent 樂意變強,不樂意變零件 —— 這是產品定位,不是技術債。
>
> 而如果你就是要讓成品 agent 當零件,你就得自己造那顆螺絲。
> 那顆螺絲,就是 `bell.py`。

## 第 10 章:那四條執行緒為什麼不會打架 —— GIL 與鎖

第 8 章的敲鈴器裡,同時有四件事在跑。這一章回答一個很自然的問題:
**它們會不會互相踩到?**

### 先看一場災難

想像你正在打字,打到一半:

```
幫我看一下
```

**就在同一瞬間**,鈴聲也要送進去:

```
[A2A-BELL] 房間到 #42(你是 alice)
```

兩邊寫的是同一條通道。如果沒有人管秩序,結果可能長這樣:

```
幫我看[A2A-BELL] 一下房間到 #42
```

**兩邊都毀了** —— 你的話被截斷,鈴聲也認不出來。而且這種錯不是每次都發生,
它只在「剛好同時」的時候出現。(是的,又是第 4 章那隻怪:race condition。)

### 解法:一把鎖

**一把鎖 = 一次只准一個人進去的房間。**

生活裡就是廁所門鎖:你進去反鎖,別人在外面等,你出來他才能進。
沒有人需要協調,門鎖自己就把秩序建立起來了。

程式裡長這樣:

```python
with lock:
    做那件不能被打斷的事
```

`with` 的意思是**進去時上鎖、離開時自動開鎖** —— 而且**就算中間程式出錯也一定會開**。

這一點比看起來重要:忘了開鎖的話,所有人會永遠卡在門外,而且程式不會報錯、
只是安靜地停住。用 `with` 就從結構上不可能忘記(又是第 4 章那招:讓錯誤無從發生)。

---

### 但這裡冒出一個問題

等一下 —— 我們有 12 個 CPU 核心,所以四條執行緒是**真的同時**在跑嗎?

答案有點反直覺,而且它有個名字。

### GIL:整間廚房只有一支鍋鏟

Python 有一把全域的鎖,叫 **GIL**(Global Interpreter Lock,全域直譯器鎖)。
規則只有一句:

> **同一時間,只有一條執行緒能執行 Python 程式碼。**

打個比方:廚房裡有 12 個爐子(12 核),你請了 4 個廚師(4 條執行緒),
**但整間廚房只有一支鍋鏟**。誰拿到鏟子誰才能炒,其他人只能站著等。

所以 Python 的多執行緒是**分時多工**(輪流做、切換得很快),
不是**真平行**(真的同時做)。

> **這條規則要限定版本,不然它會過期**
>
> 本章講的是 Python 的**標準版本** —— 也就是 `uv` 預設裝給你的那個。
>
> **Python 3.13 起,官方另外提供了一個實驗性的「無 GIL」版本**(叫 free-threaded)。
> 在那個版本裡,上面那條規則不成立:執行緒真的可以同時執行 Python 程式碼。
> 它目前仍是實驗性質、預設不會裝到 —— 但如果你哪天讀到「Python 沒有 GIL 了」,
> 講的就是它。
>
> (寫這一章時實測過:這台機器跑 Python 3.14,**GIL 是開著的**。
> 想自己查的話,新版 Python 有 `sys._is_gil_enabled()` 可以問。)
>
> ★ **但有一件事千萬別誤會**:GIL 消失**不代表可以不用鎖,反而是更需要鎖**。
> 理由見本章後面那節「那既然有 GIL,為什麼還需要鎖?」——
> 那裡講的「一行加法其實是三步、中間會被切斷」的問題,
> **在沒有 GIL 的世界只會更容易發生,不會消失。**

### 用數字說話

（2026-07-26 實測,Python 3.14,12 核機器)

**實驗一:讓執行緒一直算數學(CPU 密集)**

| 做法 | 花費時間 |
|---|---|
| 一條執行緒做四份 | 0.66 秒 |
| 四條執行緒各做一份 | 0.64 秒 |

**幾乎沒有變快。** 12 個核心閒著,因為四個廚師在搶同一支鏟子。

**實驗二:讓執行緒一直等(IO 密集)**

| 做法 | 花費時間 |
|---|---|
| 一條執行緒等四次 | 2.00 秒 |
| 四條執行緒各等一次 | 0.50 秒 |

**快了將近四倍**,幾乎是理論上限。

### 為什麼差這麼多?因為「等待」時會把鏟子放下

廚師在等水滾的時候,他手上不需要鏟子 —— 所以他會放下,讓別人先炒。

程式裡的「等待」包括:等網路回應、等檔案讀完、等使用者按鍵、`sleep` 到時間。
這些時候執行緒**根本不需要執行 Python 程式碼**,GIL 自然就交出去了。

一句話總結:

| 你的程式在做什麼 | 多執行緒有用嗎 |
|---|---|
| 一直在**算** | ❌ 沒用(要改用多**行程**,每個行程有自己的鏟子) |
| 一直在**等** | ✅ 非常有用 |

### 我們的四條執行緒,全部都在等

| 執行緒 | 在做什麼 |
|---|---|
| 盯直播 | 等 hub 送訊息來 |
| 節拍器 | `sleep` 五秒 |
| 轉發按鍵 | 等你按鍵盤 |
| 轉發畫面 | 等子行程吐東西 |

**四條全部都在等。** 所以 GIL 對敲鈴器完全不構成問題。

這不是運氣,是因為它的工作本質就是「守著幾個入口,誰有動靜就處理」——
沒有任何一條在算數學。**選對工具的意思,就是讓工具的短處剛好用不到。**

---

### 那既然有 GIL,為什麼還需要鎖?

這是最容易誤解的一點,值得單獨講。

既然同一時間只有一條執行緒能跑 Python,那不是天然就不會打架了嗎?

**不是。因為 GIL 保證的是「一小步不會被切斷」,不是「你那三行不會被切斷」。**

看這一行:

```python
self.rings_this_gap += 1
```

它看起來是一件事,實際上是三步:**讀出來 → 加一 → 寫回去**。
執行緒可能在任何兩步之間被換下去。於是:

```
執行緒 A 讀出 5
執行緒 B 讀出 5      ← 還沒等 A 寫回去
執行緒 A 寫回 6
執行緒 B 寫回 6      ← A 那次加法憑空消失了
```

敲了兩次,計數只加了一。**GIL 擋不住這個,只有鎖能擋。**

> **記住這句就好:GIL 決定「能不能同時跑」,鎖決定「會不會互相踩到」。
> 兩件不同的事,不能互相代替。**

---

### 這個專案裡的三把鎖

| 鎖 | 保護什麼 | 誰在搶 |
|---|---|---|
| `write_lock`(bell.py) | 往子行程寫字的那條通道 | 你打字 vs 敲鈴 |
| `BellState.lock`(bell.py) | 鈴聲的計數與上次敲的時間 | 盯直播 vs 節拍器 |
| `post_lock`(server.py) | 聊天室的寫入 | 所有同時發言的人 |

### 實務原則一:鎖保護的是「資料」,不是「程式碼」

很多人以為鎖是在「保護這幾行」。其實它保護的是**那份會被多人同時碰的資料**。

判斷方法就一句話:**問「哪份資料會被兩個以上的人同時改?」**
那份資料就需要一把鎖,而所有會碰它的地方都要用**同一把**。

用不同的鎖保護同一份資料,等於沒鎖 —— 就像兩間廁所共用一個馬桶,各自上各自的門鎖。

### 實務原則二:鎖裡面放越少越好

看伺服器收到一則發言時做的事:

```python
async with self.post_lock:
    ...檢查、寫檔...

# ★ 鎖放掉之後才做這兩件
self.bus.publish(room, msg)          # 通知所有正在看的人
self.a2a_layer.on_room_message(...)  # 通知協定層
```

**廣播是故意放在鎖外面的。**

因為廣播可能要通知幾十條連線,如果放在鎖裡面,**所有想發言的人都得排隊等它跑完**。
而廣播根本不改共用資料,它不需要排隊。

> **鎖握得越久,大家等得越久。鎖裡面只放「非排隊不可」的事。**

### 最後:鎖的風險是死鎖

兩個人各拿一把鎖,又互相等對方手上那把 —— **兩邊永遠動不了**,而且程式不會報錯,
只是安靜地停住。這叫 **deadlock(死鎖)**,是多執行緒最難查的一類問題。

**我們怎麼避免的**:三把鎖都很「淺」—— 進去做一件小事就出來,
**絕不在拿著一把鎖的時候去拿另一把**。

只要沒有人同時握兩把,那個「互相等」的環就無從形成 ——
又一次,不是靠小心翼翼,是靠讓它不可能發生。

技術上,這是一個合格的 A2A 協定實作 + 一個賽博龐克風的聊天室介面。
但它更有意思的地方在於**它是怎麼被做出來的**:

三個 AI agent(alice 管美感、bob 管嚴謹、dev 管實作)在這個聊天室裡**互相審查、
吵架、驗收**,一輪一輪把系統從「能跑」磨到「能維護」再到「能開門」。
人類(你)只需要下方向、做最後拍板。

不是因為算力更多,而是因為**有人跟你唱反調時,錯誤藏不住。**
